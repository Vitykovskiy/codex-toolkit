# Пакт UI-анализа

Этот документ задает обязательный порядок анализа и документирования поведения UI.

Пакт применяется к описанию Vue-экранов, компонентов, элементов управления, таблиц, форм, модальных окон, пустых/ошибочных состояний, offline read-only и responsive-поведения.

Общие требования к форме, актуальности, минимальному diff и ссылкам задает [пакт документации](documentation-pact.md). Этот документ добавляет только требования к содержанию UI-описания.

## Главный закон

UI-документация фиксирует наблюдаемое поведение интерфейса так, чтобы разработчик мог изменить компонент без догадок о состояниях, действиях пользователя и граничных случаях.

Описание UI считается неполным, если из него нельзя понять:

- за что отвечает элемент;
- какие действия пользователя он принимает;
- какие состояния он имеет;
- что происходит с данными, текстом, ошибками и layout в граничных случаях;
- где проверить это поведение в коде, тестах или требованиях.

## Источники проверки

Перед фиксацией UI-поведения агент сверяет факты с релевантными источниками:

- текущая реализация: template, TypeScript, SCSS, shared-компонент, фасад;
- тесты рядом с компонентом;
- локальная документация `docs/`;
- `TECHNICAL_SPECIFICATION.md`, `contracts/openapi.yaml` и локальные UI-нoты, если речь о целевом поведении или требованиях.

Факт реализации и целевое требование фиксируются раздельно. Если код, API и требования расходятся, документация явно помечает расхождение.

## DoD UI-описания

UI-описание считается принятым только при выполнении всех критериев:

- **DoD: ГРАНИЦА ОПИСАНА.** Указано, что именно описывается: экран, область экрана, компонент, элемент управления или состояние.
- **DoD: ОТВЕТСТВЕННОСТЬ ОПИСАНА.** Для элемента указано, за что он отвечает, какие данные показывает, какие события наружу отправляет и где проходит граница ответственности.
- **DoD: ДЕЙСТВИЯ ПОЛЬЗОВАТЕЛЯ ОПИСАНЫ.** Зафиксированы поддерживаемые действия: клик, двойной клик, ввод, выбор, сброс, открытие, закрытие, подтверждение, отмена, переход, submit.
- **DoD: СОСТОЯНИЯ ОПИСАНЫ.** Для релевантного элемента указаны состояния из фактического набора: default, hover, focus, active, selected, disabled, readonly, loading, empty, error, dirty, invalid, open, closed.
- **DoD: ПЕРЕХОДЫ МЕЖДУ СОСТОЯНИЯМИ ОПИСАНЫ.** Указано, какое действие, входной параметр, ответ API или внутреннее состояние переводит UI в новое состояние.
- **DoD: ВИДИМЫЙ РЕЗУЛЬТАТ ОПИСАН.** Для каждого действия и состояния понятно, что видит пользователь: текст, иконку, tooltip, popover, диалог, баннер, spinner, validation message, toast или навигацию.
- **DoD: ДАННЫЕ И СОБЫТИЯ ОПИСАНЫ.** Указано, какие входные данные влияют на отображение, какие события/значения уходят наружу и какие API-данные участвуют в UI, если это важно для поведения.
- **DoD: ГРАНИЧНЫЕ СЛУЧАИ ОПИСАНЫ.** Для UI с переменным содержимым указано поведение при длинном тексте, пустом значении, большом количестве элементов, узком viewport, переполнении, scroll, wrap, ellipsis, line-clamp и наложении иконок.
- **DoD: RESPONSIVE-ПОВЕДЕНИЕ ОПИСАНО.** Если поведение зависит от ширины экрана или устройства, указаны breakpoint, отличие действий и отличие layout.
- **DoD: ОШИБКИ И ПУСТЫЕ СОСТОЯНИЯ ОПИСАНЫ.** Для загрузки данных указаны loading, empty, filter-empty, error, offline read-only и retry/close/reset-действия, если они есть.
- **DoD: ВАЛИДАЦИЯ ОПИСАНА.** Для форм и editable-элементов указаны обязательность, формат, маска, уникальность, min/max, момент показа ошибки и блокировка действий.
- **DoD: ДОСТУПНОСТЬ ЗАФИКСИРОВАНА.** Если в реализации есть keyboard, focus, aria-label, aria-expanded или role, документация указывает это как часть поведения.
- **DoD: ИСТОЧНИК ПРОВЕРКИ УКАЗАН.** Рядом с поведением есть путь к коду, тесту, ноте или требованию, где это можно проверить.
- **DoD: НЕПОДТВЕРЖДЕННОЕ НЕ ВЫДАНО ЗА ФАКТ.** Поведение, которого нет в коде или проверенном источнике, фиксируется как gap, требование или вопрос, а не как реализованная возможность.

Если хотя бы один релевантный критерий не выполнен, UI-описание считается непринятым.

## Минимальная форма UI-блока

Для небольшого элемента достаточно короткой таблицы или списка:

```markdown
### <Элемент>

| Что | Поведение |
|---|---|
| Ответственность | ... |
| Действия | ... |
| Состояния | ... |
| Длинный/пустой контент | ... |
| Источник проверки | ... |
```

Для экрана описание делится на области: shell, toolbar, основной контент, формы/таблицы, модальные окна, состояния загрузки и ошибки.

## Рабочая формула

Перед сдачей UI-документации агент проверяет:

> Если разработчик меняет этот элемент, понятно ли из документации, какие состояния и граничные случаи должны сохраниться?

Если ответ отрицательный, UI-описание нужно дополнить или связать с правильным источником проверки.
