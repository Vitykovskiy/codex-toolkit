# Эксперимент: Crapper, Dryer и Mutator

Используй эту процедуру по прямому запросу на инструменты или при явном включении эксперимента в правилах проекта. Владелец изменения выбирает один небольшой модуль либо файл и вопрос, который нужно проверить; reviewer оценивает результаты в рамках своей уже назначенной приёмки. Сохраняй разрешённый режим и write-set. Обычная правка кода сама по себе эксперимент не включает.

## Назначение

| Инструмент | Наблюдение | Следующее решение |
|---|---|---|
| Crapper | Сложность функции, покрытие и `CRAP = CC² × (1 − coverage)³ + CC` | Найди причину риска: ветвление, непроверенное поведение или оба фактора. |
| Dryer | Пары структурно похожих фрагментов | Установи, выражают ли они одно правило с одной причиной изменения. |
| Mutator | Реакция тестов на временные изменения операций в коде | Разбери выполненные, выжившие и непокрытые мутации. |

Инструменты дают измерения и отчёты. Постоянное изменение структуры выполняет разработчик в разрешённой области по [стандарту читаемости](development-pact.md#человекочитаемый-код). Дробление функции и объединение похожего кода требуют предметного основания; числовой порог сам по себе такого основания не создаёт.

## Подготовка

1. Установи поддерживаемый язык, конкретные существующие пути, команды тестов и способ получения покрытия из проекта. На проверенных версиях все три инструмента поддерживают Clojure, Java, Go, TypeScript, Rust и Python. Crapper и Mutator также принимают JavaScript; у Dryer расширения `.js`, `.jsx`, `.mjs`, `.cjs` отсутствуют. Markdown, YAML и TOML toolkit не образуют подходящий тестовый проект для этих инструментов.
2. Используй уже подготовленные инструменты либо действующее разрешение на их установку. Проверенные версии требуют Python 3.11+, `tree-sitter` и `tree-sitter-language-pack`. Upstream launcher при первом запуске, включая `--help`, создаёт собственную `.venv` и устанавливает зависимости. Для Mutator нужен также Crapper: установленный в его Python-среде либо соседний checkout `../crapper`. Изменение этой инструкции не устанавливает инструменты в потребителей.
3. Подготовь грамматики tree-sitter для выбранного языка. Crapper и Dryer вызывают `download([language])` перед получением парсера; Mutator использует Crapper. Даже подготовленный executable при анализе, включая `--no-coverage` или `--scan`, может потребовать сетевую загрузку отсутствующей грамматики и запись кеша. Используй уже доступные парсеры либо действующее разрешение на загрузку и место кеша; при недоступности зафиксируй причину и оставь зависимый прогон невыполненным.
4. Зафиксируй ревизии инструментов и проекта в существующем отчёте. Проверенные исходные ревизии приведены в [источниках](#источники); при другой версии сверь её CLI и побочные эффекты. Для первого прогона выбери отдельную рабочую копию без чужих незакоммиченных изменений и параллельных писателей.
5. До мутаций проверь обычные тесты без изменений и пригодность тестовой среды. Тесты должны читать код из текущей рабочей копии; абсолютные пути к исходному проекту, установленный вместо локального пакет или старый build могут обойти мутант. Для `--test-command` проверь доступность executable из worker: каталоги `.venv` и `venv` туда не переносятся, поэтому относительный `.venv/bin/python` там отсутствует. Можно использовать абсолютный путь к интерпретатору, сохранив загрузку исходников относительно worker. Устрани такую неоднозначность до прогона. Внешние записи и общие ресурсы тестов должны входить в уже разрешённую область.

Начинай с явных существующих путей. У всех трёх `--changed` выбирает изменения из `git status`, включая untracked, а не diff закоммиченного PR с его базой. У Dryer этот режим сравнивает только выбранные изменённые файлы между собой. Для сравнения с соседним кодом укажи оба пути. Несуществующий позиционный аргумент трактуется как текстовый фильтр и может дать пустую выборку.

## Команды первого прогона

Запускай из корня выбранного проекта. Ниже `CRAPPER`, `DRYER`, `MUTATOR` — абсолютные пути к подготовленным launcher-файлам или установленным executable; `SOURCE_FILE` — существующий исходный файл, `SOURCE_DIR` и `RELATED_DIR` — существующие связанные каталоги, `TEST_COMMAND` — подтверждённая команда тестов из корня проекта. Подставь фактические значения до запуска. Команды используют имеющееся покрытие, чтобы отдельно контролировать его получение и результат тестов.

### Crapper

Сначала получи свежий отчёт покрытия существующей разрешённой командой проекта. Сверь, что он относится к текущим исходникам, выбранным тестам и ожидаемым путям. Затем выполни:

```bash
"$CRAPPER" --use-existing-coverage "$SOURCE_FILE"
```

Читай таблицу и `.metrics/crap.edn`. Для первого эксперимента используй CRAP 10 как ориентир для разбора функций; обязательный порог задаёт проект. Флаг `--threshold 10` возвращает ошибку только при значении **выше** 10, поэтому не реализует строгое правило «меньше 10» из ub-mode. Исправление может состоять в проверке существенного поведения или в прояснении структуры; сохраняй обоснованное ветвление.

Если покрытие недоступно, разрешён отдельный ограниченный замер:

```bash
"$CRAPPER" --no-coverage "$SOURCE_FILE"
```

В этом режиме доступны только показатели сложности: покрытие и CRAP имеют значение N/A. Отсутствующий отчёт при `--use-existing-coverage` может выглядеть как 0%, что не доказывает выполненный тест. Обычный запуск Crapper без этих флагов способен пересоздать отчёты, запустить тесты и автоматически установить дополнительные coverage-пакеты. Используй его только при применимом разрешении на эти действия. Код завершения Crapper не доказывает успешность тестов: проверяй их собственный результат отдельно.

### Dryer

```bash
"$DRYER" --threshold 0.8 "$SOURCE_DIR" "$RELATED_DIR"
```

Читай пары в stdout и `.metrics/dry.edn`. Порог 0.8 взят как экспериментальный ориентир ub-mode; CLI по умолчанию использует 0.82. Также действуют фильтры размера: минимум 4 строки и 20 нормализованных синтаксических узлов. Отсутствие пары не доказывает отсутствие любых повторов.

Похожие формы — кандидаты для разбора. Сверь предметный смысл и причины изменения по действующему DRY-правилу; сохрани разные ответственности и понятные границы. Exit 0 означает сформированный отчёт и возможен при найденных дублях.

### Mutator

Сначала посмотри объём выбранной работы:

```bash
"$MUTATOR" --scan --no-coverage "$SOURCE_FILE"
```

`--scan` выводит места мутаций без тестов и записи метрик. `--no-coverage` без `--scan` **разрешает выполнение мутаций без фильтра покрытия**; этот флаг сам по себе не является пробным запуском.

Перед выполнением проверь `target/mutator-backup/`: обычный запуск восстанавливает оставленные старой версией backup-файлы в исходники. При таких остатках останови этот прогон и сохрани рабочие данные; выясни их происхождение перед восстановлением. Worker-каталоги в `target/mutation-workers` содержат отдельную копию мутируемого файла и ссылки на часть проекта. Это не изоляция внешних сервисов или побочных эффектов тестов.

При успешной исходной проверке тестов и свежем покрытии выполни ограниченный прогон:

```bash
"$MUTATOR" --use-existing-coverage --mutate-all --max-workers 1 \
  --test-command "$TEST_COMMAND" "$SOURCE_FILE"
```

Начни с одного файла; при большом числе мест сузь выборку поддерживаемым `--lines`. `--max-workers 1` ограничивает параллелизм. `--mutate-all` повторяет ранее убитые мутанты: обычный кеш учитывает текст функции и может сохранить старые результаты после изменения только тестов. Команда тестов выполняется из корня проекта, затем из соответствующего worker; она должна фактически загружать изменённый файл.

Разбери `.metrics/mutate/<namespace>.edn` вместе с выводом и исходным результатом тестов:

- `killed`: тест упал или истёк таймаут. Ошибка импорта, окружения или некомпилируемый мутант также могут дать этот статус; сам он не устанавливает причину падения.
- `survived`: тесты прошли. Установи, меняет ли мутация требуемое поведение на допустимых входах. Исправляй содержательный пробел только в разрешённой области; эквивалентный мутант требует объяснения, а не теста ради числа.
- `uncovered`: место не покрыто и обычно не выполнялось. Процент `killed / (killed + survived)` исключает такие места, поэтому высокий процент не закрывает их.

Эта ревизия Mutator не сохраняет и не выводит сообщения о падении тестов отдельных мутантов; `--verbose` показывает команды и мутации. Исходные тесты проверяются в реальном дереве проекта, поэтому их успех не исключает ошибку только внутри worker. Устанавливай причину `killed` доступным уже разрешённым способом диагностики; если её подтвердить нельзя, укажи непроверенную причину, сохранив фактический статус инструмента. По одному отчёту не объявляй содержательность теста доказанной.

Exit 3 сообщает о выживших мутантах; exit 2 может означать сбой исходных тестов или отсутствие Crapper. Exit 0 возможен при нулевой выполненной работе. Всегда укажи число выбранных и реально выполненных мутаций, пропуски, непокрытые места и состояние исходных тестов. При отсутствии мест мутаций исходные тесты могут вообще не запускаться. Ошибка среды, пустая выборка и только кешированные результаты не подтверждают новый успешный прогон.

## Завершение и отключение

Сохрани в существующем отчёте область, ревизии, команды и фактические результаты, свежесть покрытия, существенные находки и ограничения. Для разрешённых исправлений используй [критерий содержательности тестов](development-pact.md#содержательность-тестов); новые тесты и автоматизация требуют полномочий по [общему правилу](../../codex-orchestration-pact/SKILL.md#general-rule-for-verification-means). После мутаций сверь рабочие изменения: ожидаемые отчёты не должны скрывать изменение исходников.

Остановись после выбранного прогона и решения по его находкам. Недоступный executable, неподдерживаемый язык, отсутствие пригодного покрытия или неуспешные исходные тесты обозначь точной причиной; продолжай независимые разрешённые проверки. Не превращай эксперимент в непрерывное исправление всего проекта или обязательный CI-gate. Чтобы отключить его, убери явное включение из правил проекта либо прекрати вызывать эту процедуру; общий критерий содержательности тестов продолжает действовать.
