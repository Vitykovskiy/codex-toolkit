# Пакт разработки

Этот документ задает обязательный пакт работы с кодом проекта.


## Главный закон

Код должен быть прямым, читаемым и проверяемым.

Если решение выглядит сложным, громоздким, неуместным по месту изменения или требует догадок о скрытом поведении, это проблема реализации. Такой код упрощается, переносится в правильный слой, покрывается тестом или выносится на обсуждение с пользователем.

## Источники требований

Перед нетривиальной правкой кода Codex сверяет решение с фактическим состоянием проекта и документами:

1. ADR, если правка затрагивает архитектурный паттерн.
2. Существующий код и тесты в той же области.

Задокументированные требования к коду обязательны. Если требование не подходит к текущей задаче, Codex сначала показывает конфликт пользователю и предлагает корректный вариант.

## Критерий качества

Готовый код должен отвечать на вопросы без чтения переписки:

- что делает изменение;
- где входят и выходят данные;
- какой слой владеет состоянием;
- почему код находится именно здесь;
- как проверяется корректность;
- какие проектные правила он соблюдает.

## Критерии приемки правки кода

Правка кода считается принятой, если:

- изменение реализует текущую задачу без неподтвержденных будущих сценариев;
- код расположен в слое, который владеет этой ответственностью;
- зависимости между файлами соблюдают границы слоев и принятое направление внутри фичи;
- публичные контракты, API, модели и состояние сохраняют текущее поведение для существующих потребителей; breaking change допускается только после явного согласования;
- данные из API, storage, URL и `history.state` проверяются перед использованием в доменной модели или UI-состоянии;
- сложность решения соответствует задаче: нет лишних абстракций, универсальных типов и скрытых фоллбеков;
- код читается по месту изменения: сложные или повторяющиеся условия вынесены в именованные функции, константы или производные значения;
- шаблон и методы используют готовое производное значение, если одно и то же условие нужно больше одного раза;
- вложенные условия упрощены ранним выходом, если это делает основной сценарий короче и понятнее;
- в рабочем изменении нет сфокусированных или отключенных тестов (`fit`, `fdescribe`, `xit`), временных TODO и отладочного кода;
- итоговый diff минимален и не затрагивает чужие несвязанные изменения.

## Читаемость

- Имена отражают предметный смысл, а не техническую механику.
- Функции и методы держат один уровень ответственности.
- Ветвления, вложенность и обобщенные типы (`generic`) остаются настолько простыми, чтобы код читался без расшифровки автором.
- Дублирование устраняется только понятной абстракцией с реальными текущими потребителями.
- Комментарий объясняет ограничение, инвариант или причину решения; очевидный код комментарием не пересказывается.

## Фоллбеки и обходы

`fallback` (фоллбек) — резервное поведение при допустимом варианте внешнего контракта. Он допустим только при всех условиях:

- вариант реально описан контрактом или подтвержден текущим кодом/API;
- логика вынесена в явно названную вспомогательную функцию;
- при нарушении текущего API-контракта код выдает contract error — ошибку нарушения контракта, а не молча угадывает данные.

Костыль, временный обход или поведение «на всякий случай» требует явного обсуждения с пользователем. Без обсуждения такой код не добавляется.

## Мапперы и внешние данные

- Данные внешнего API считаются недоверенными во время выполнения.
- `mapper` (маппер) на границе API проверяет обязательные поля, union-значения и структурные инварианты через type guard или assertion helper.
- Маппер преобразует внешний контракт в доменную модель фичи; он не содержит UI-состояние, HTTP, навигацию и побочные эффекты.
- Сложный маппер считается сигналом проблемы: нужно упростить контракт преобразования, разделить этапы или обсудить API/модель с пользователем.

## Абстракции

Новая абстракция допустима, когда она снимает реальную текущую сложность и сохраняет границы слоев.

Стоп-сигналы для обобщения:

- обобщение тащит специфичные для фичи DTO или поля в `shared`;
- обобщенные типы (`generic`) становятся сложнее исходного кода;
- базовый класс нужен только ради формы, а не ради общего поведения;
- новый параметр или точка расширения обслуживает гипотетического будущего потребителя;
- поиск поведения в коде становится заметно сложнее.

Для UI и shared-логики применяется `rule of three` (правило трех потребителей): общий слой появляется после трех реальных потребителей либо после доказанного посимвольного дубля с одинаковым контрактом.


## Код без будущего

Код пишется под текущую задачу и подтвержденные требования.

Без обсуждения с пользователем Codex не добавляет:

- конфигурацию без текущего потребителя;
- необязательный API под возможный backend;
- универсальный `generic` вместо конкретной модели;
- ветку обработки гипотетического состояния;
- TODO, который скрывает незавершенное решение.

## Тесты

Тесты проверяют поведение и проектные инварианты.


- Тесты лежат рядом с тестируемым файлом.
- Имена тестов и UI-ассерты пишутся на русском.
- `fit`, `xit`, `fdescribe` не попадают в рабочее изменение.

## Перед завершением

Codex проверяет рабочее изменение по списку:

- задокументированные code-style правила соблюдены;
- DTO не протекли в UI;
- внешний контракт проверяется на границе;
- нет молчаливых фоллбеков и костылей;
- нет кода под гипотетическое будущее;
- место изменения соответствует слоям проекта;
- документация обновлена, если правка нетривиальная.

## Протокол исправления

Если пользователь указывает, что код сложный, громоздкий, нечитабельный, похож на костыль или стоит не в том месте, Codex обязан:

1. остановить текущий вариант;
2. показать, какое правило нарушено;
3. упростить код или предложить перенос ответственности;
4. убрать неподтвержденные фоллбеки и будущие ветки;
6. обновить документацию, если меняется техническое устройство.

## Рабочая формула

Перед сохранением кода Codex проверяет:

> Этот код можно поддерживать через месяц без знания переписки и без догадок о намерениях автора?

Если ответ отрицательный, код надо упростить, сузить или обсудить с пользователем.
