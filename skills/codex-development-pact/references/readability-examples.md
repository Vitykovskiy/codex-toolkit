## Решение по нескольким причинам

Ниже адаптирован принятый пользователем пример `shouldNotify`. Для обоих вариантов задан один учебный контракт: локальные ошибки, 401, отмена и неактуальный запрос не создают общего уведомления; операции чтения сообщают о `status === 0` и статусах от 500, остальные операции — об оставшемся HTTP-сбое. Необязательная `isCurrent` проверяет актуальность; её отсутствие допускает дальнейшее решение. В примере 401 принадлежит владельцу авторизации, ошибки 4xx при чтении — экрану.

Имена `HttpErrorResponse`, `HttpStatusCode`, `HttpErrorNotificationMetadata` и `isAborted` обозначают существующие типы и проверку исходного примера. Это фрагменты для чтения, а не самостоятельная программа или новая зависимость toolkit. Здесь сравнивается структура при одинаковом контракте; более ранний вариант interceptor из исходного запроса имел другую политику уведомлений.

**Вариант, требующий мысленного разбора:** причины раннего отказа объединены, роль `metadata` приходится уточнять, а решение о чтении выражено через отрицание промежуточного флага.

```typescript
function shouldNotify(error: unknown, metadata: HttpErrorNotificationMetadata): boolean {
  if (
    !(error instanceof HttpErrorResponse) ||
    error.status === HttpStatusCode.Unauthorized ||
    isAborted(error) ||
    metadata.isCurrent?.() === false
  ) {
    return false;
  }

  const isRead = ['load', 'check', 'unique-check', 'download'].includes(
    metadata.operation ?? 'action'
  );
  return !isRead || error.status === 0 || error.status >= HttpStatusCode.InternalServerError;
}
```

**Предпочтительная форма:** контракт объясняет роли входов, причины отказа видны отдельно, выбор по операции читается непосредственно.

```typescript
/**
 * Определяет, нужно ли общее уведомление об ошибке запроса.
 *
 * @param error - Ошибка из цепочки запроса; локальные исключения не создают HTTP-уведомление.
 * @param notificationOptions - Настройки уведомления из контекста запроса:
 *   operation задаёт вид действия; isCurrent проверяет, нужен ли его результат
 *   текущему экрану или сессии. Без isCurrent запрос считается актуальным.
 * @returns true, если HTTP-сбой нужно показать общим уведомлением.
 */
function shouldNotify(error: unknown, notificationOptions: HttpErrorNotificationMetadata): boolean {
  if (!(error instanceof HttpErrorResponse)) {
    return false;
  }

  // 401 передаётся владельцу авторизации: он восстанавливает или завершает сессию.
  if (error.status === HttpStatusCode.Unauthorized) {
    return false;
  }

  if (isAborted(error)) {
    return false;
  }

  // После смены экрана или сессии ошибка прежнего запроса уже не нужна пользователю.
  if (notificationOptions.isCurrent?.() === false) {
    return false;
  }

  switch (notificationOptions.operation) {
    case 'load':
    case 'check':
    case 'unique-check':
    case 'download':
      // При чтении сообщаем о недоступности сервера; ошибки 4xx обрабатывает экран.
      if (error.status === 0) {
        return true;
      }

      return error.status >= HttpStatusCode.InternalServerError;
    default:
      // Команда должна сообщить пользователю об ошибке выполнения действия.
      return true;
  }
}
```

## Что проверять в сравнении

- **C1:** `notificationOptions` раскрывает роль объекта, сохраняя существующий тип.
- **C2–C3:** основания отказа и выбор операции видны сверху вниз. Для чтения решения не требуется отдельная цепочка вспомогательных функций или разворачивание `!isRead`.
- **C5–C6:** JSDoc объясняет источник ошибки, смысл необязательной функции и результата; комментарии у ветвей объясняют причины.
- **Сохранение контракта:** `isAborted` и `isCurrent` вызываются в прежнем порядке после предшествующих проверок. Исключение из `isCurrent` продолжает распространяться. Отсутствующая операция и `action` доходят до того же результата. Эти соответствия можно сопоставить по исходникам; исполнение сценария здесь не заявлено.

Сама `shouldNotify` возвращает решение; показ уведомления принадлежит вызывающему коду. Пояснения об авторизации и экране допустимы благодаря заданному контракту примера. В рабочем проекте проверь таких владельцев по его источникам, прежде чем переносить текст комментария.

Сохраняй простое выражение, когда оно понятно непосредственно. Правило не вводит общего запрета `&&`, `||`, `??`, `includes`, тернарного оператора, `switch` или `boolean`. Число строк и комментариев не является мерой успеха. Выделение вспомогательной функции полезно, когда раскрывает самостоятельный смысл и уменьшает стоимость чтения.

## Простая операция

Учебный контракт этой функции — удалить крайние пробелы из переданной строки:

```typescript
function normalizeTitle(title: string): string {
  return title.trim();
}
```

Назначение и результат видны из имени и одного действия. Сохрани такую форму: промежуточный флаг, обёртка для `trim()` или JSDoc, пересказывающий сигнатуру, не добавят смысла. Неочевидное условие реального контракта потребует своего пояснения.
