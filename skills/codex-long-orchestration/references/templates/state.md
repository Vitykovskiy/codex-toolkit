# Компактное состояние dispatcher_only

Только root атомарно пишет один `state.md` в task_root. В нём остаются режим, ссылки на request/goal, очередь переходов, активные назначения, резервы ресурсов, завершённые и принятые результаты, checkpoint, препятствия и известный расход; все предметные файлы и отчёты остаются по ссылкам, root не читает ни их содержимое, ни фрагменты. См. [обязательный инвариант диспетчера](../../../codex-orchestration-pact/SKILL.md#dispatcher-invariant). State содержит только процессные поля и ссылки, без пересказа задачи и предметных выводов. Старый running, дубликат envelope и изменение транзитивного входа требуют проверки процессных метаданных; актуальность предметных входов проверяет назначенная роль до зависимой работы.

`next_transitions` — очередь готовых и ожидающих зависимостей дескрипторов из [envelope](envelope.md). `active_assignments` сохраняет ID/attempt, исходную ревизию запуска, связанные снимки входов, `runtime_handle` и текущий native-статус. `completed_assignments` хранит процессные receipts с ID/attempt, goal version, snapshot и ссылкой отчёта; `accepted_results` — точные корреляции независимой приёмки. `resource_reservations` связывает ID ресурса, режим read/write и держателя с попыткой. Это текущее состояние, не полный журнал событий. Все поля заполняются из разрешённых метаданных, без извлечения из предметных файлов.

Перед запуском root резервирует назначение и ресурсы; после подтверждённого окончания освобождает их и проверяет только соответствующие зависимости очереди по [Parallel execution](../../../codex-orchestration-pact/references/parallel-execution.md). Свободная ёмкость определяется клиентом; нового числового лимита toolkit нет. Дубликат receipt не создаёт второй запуск или приёмку. Изменение `plan_revision` само по себе не отменяет незатронутые результаты и активные назначения: сопоставляй receipt с сохранённой ревизией его запуска. Сохраняй выданный владельцем список `invalidated_assignments` с ID/attempt и ревизией; затронутые receipts и приёмка больше не открывают зависимости, но их артефакты сохраняются для перепроверки. Отмена запрошена — ещё не подтверждённая остановка; до неё сохраняй резервы.

`cost` хранит только известное состояние разрешённого расхода, а не обязательный пользовательский бюджет, журнал событий или сборщик токенов. Если пользователь не задал лимит, оставь `limit: not_set` без отдельного согласования. Если лимит задан, перед каждым запуском используй общий известный остаток и действующие резервы всех активных назначений; один остаток не выдаётся каждой ветке заново. `launch_set` отмечает текущий набор запусков и не обнуляет резервы ещё активной работы. `cumulative` сохраняется между сессиями, стратегиями и партиями. `increments` с устойчивым ключом описывают только приращения названной области; значение переносится в `cumulative` не более одного раза. Ненаблюдаемый расход, остаток или резерв равен `unknown`, а не нулю; отсутствие необязательной телеметрии само по себе не останавливает разрешённую работу.

Для каждого активного или неразрешённого blocker state хранит устойчивый `finding_id`, а не только его отображаемое имя: ID нарушенного критерия, если он передан как процессное поле, последнее `progress` (`confirmed`, `none` или `unknown`), `consecutive_without_confirmed_progress` и, при `none`/`unknown`, `no_progress.missing_input` и `no_progress.next_check`. Root переносит эти поля из envelope; `none` и `unknown` увеличивают счётчик, `confirmed` обнуляет его. Дубликат уведомления не изменяет счётчик. Смена сессии, assignment или имени finding сохраняет запись с тем же `finding_id`; неудачная диагностика не создаёт новый ID. После двух последовательных попыток без подтверждённого прогресса root вызывает существующего владельца решения по тем же исходным ссылкам; явный сигнал застоя, повторов, избыточных проверок или отклонения требует коррекции раньше по [Progress and efficiency](../../../codex-orchestration-pact/SKILL.md#progress-and-efficiency). State сохраняет только ссылку и разрешённые поля подготовленного перехода, без самостоятельного выбора стратегии.

`completion` хранит последний актуальный совокупный результат владельца плана из [envelope](envelope.md): ревизию плана и подтверждённый/общий вес этапов. Root выводит приблизительный процент из их отношения; повторное уведомление заменяет снимок, а не прибавляет прогресс. `process_signal` сохраняет текущий процессный сигнал. При возобновлении сохраняй эти поля и принятые результаты; изменение плана требует новой ревизии и пересчёта владельцем. Недоступная оценка равна `null`, а не нулю. Подробности плана и обоснования проверок остаются у предметной роли. Старое состояние с отсутствующими полями читается как неизвестная оценка; обновляй его при очередной содержательной контрольной точке.

`streams` хранит по каждому `stream_id` назначенного `stream_owner` и последний актуальный `stream_completion` из [envelope](envelope.md). Очередь и активные назначения сохраняют связь с этим ID. Root вычисляет число активных потоков по различным ID подзадач с подтверждённым текущим исполнением согласно [Progress and efficiency](../../../codex-orchestration-pact/SKILL.md#progress-and-efficiency). При возобновлении восстанови связи, владельцев и оценки, сопоставь назначения с native-состоянием и выведи общий процент, число активных потоков и процент каждой активной подзадачи. При неполных связях или сведениях об активности число потоков равно `unknown`; неизвестная оценка прогресса хранится как `null`. Явный `stream_id: null` обозначает агрегирующее назначение; отсутствующее поле требует уточнения у владельца.

```yaml
version: 1
mode: dispatcher_only
goal_path: goal.md
request_sources: [sources/U001.md]
plan_revision: null
active_assignments: []
next_transitions: []
completed_assignments: []
accepted_results: []
invalidated_assignments: []
resource_reservations: []
checkpoint: null
completion: null
streams: {}
process_signal: null
cost:
  authority: not_set
  limit: not_set
  cumulative:
    tokens_spent: unknown
    subject_assignments: 0
    continuations: 0
  increments: []
  launch_set:
    id: null
    known_remaining: unknown
    reservations: []
blockers:
  - finding_id: F01
    criterion: A09
    progress: none
    consecutive_without_confirmed_progress: 1
    no_progress:
      missing_input: "Результат целевой проверки"
      next_check: "R01"
```

Это добавочные поля версии 1. При чтении старого state перенеси `next_transition` в список из нуля или одного элемента и сохрани известные running/accepted результаты. Недостающие сведения остаются неизвестными: сначала сопоставь активные handles с native-состоянием, затем получи необходимые поля у предметного владельца. Отсутствующий список не доказывает отсутствие уже запущенной работы. Возобновляй разрешённые готовые переходы без повторного запуска активных или принятых назначений; неоднозначность блокирует только затронутые, зависимые и конфликтующие работы.
