# Протокол dispatcher_only

Применяй вместе с [ядром long](../SKILL.md) и [базовой оркестрацией](../../codex-orchestration-pact/SKILL.md). В обычной локальной задаче root вправе работать сам; активный dispatcher_only запрещает этот fallback, включая финальную проверку и восстановление.

## Назначения и переходы

Decomposer оформляет точные назначения, зависимости, общие ресурсы и корректирующие назначения. Root запускает только существующее назначение с указанными входами, ролью, `write_set`, собственным отчётом и единственным разрешённым следующим шагом. Analyst может начать intake без goal; исполнитель не требует будущего отчёта reviewer. Reviewer принимает только конкретный completed-результат и не исправляет его. Изменение критериев, проверок, write-set или решения создаёт заменяющее назначение; изменение бизнес-смысла требует пользователя.

Completed реализации ведёт к reviewer; принятые части с уникальными связями — к integration_reviewer. Провал review ведёт к существующему коррекционному или диагностическому назначению, затем к decomposer при изменении границ. Ошибка формы/отсутствующий путь получает один возврат только на сериализацию. Краткое [извещение](templates/envelope.md) не является API маршрутизации и не доказывает exactly-once.

## Прогресс и расход

Для каждого blocker сохраняй устойчивый finding ID, нарушенный критерий, наблюдение/воспроизведение, ожидаемую проверку и `progress` относительно предыдущей попытки. После двух последовательных попыток без подтверждённого прогресса root направляет узкий пакет свежему владельцу: analyst для конфликта требований, `architect_astra` для технического тупика, `quality_owner_astra` для спорного продуктового/UI-решения либо назначенному техническому владельцу для установленной проблемы среды. Повтор той же консультации без нового существенного входа не запускается; полезное третье исправление разрешено.

В [state](templates/state.md) root хранит только текущую партию, активные назначения/попытки, checkpoint, препятствия, следующий шаг и сводный расход: источник разрешения, известные лимиты или `not_set`, время, число предметных поручений/продолжений, доступные/потраченные токены всех ролей и причину продолжения/паузы. Примерно каждые 30 минут на безопасной границе сохраняй checkpoint и проверяй прогресс. Достижение checkpoint не останавливает полезную работу; известный исчерпанный жёсткий лимит даёт `paused/budget`.

## Состояние, пути и повторы

Элемент active assignments ссылается на ID, роль, попытку, назначение, собственный артефакт/извещение и фактический runtime handle, когда он наблюдаем. Старый running и дубликат ответа требуют проверки исхода; новая попытка не повторяет побочное действие до этой проверки. Изменение прямого или транзитивного входа получает узкую оценку владельца, а несвязанные результаты сохраняются. Это процедурная защита, не технический исполнитель или доказательство exactly-once.

В concrete task task_root — явно установленный локальный корень. Отчёт, вопрос, назначение, state и входные ссылки задачи относительны ему: абсолютный путь и `..` запрещены, а реальная цель проверяется на containment и symlink/reparse escape. Исходный write-set относится к явно названному Git-контексту. workspace-write — процедурное право, не техническая изоляция папки.
