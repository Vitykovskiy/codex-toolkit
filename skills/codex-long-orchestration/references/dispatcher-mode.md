# Протокол dispatcher_only

## Назначение и полномочия

Применяй вместе с [ядром long](../SKILL.md) и [базовой оркестрацией](../../codex-orchestration-pact/SKILL.md). Общая приёмка, отчёт и дефектные циклы имеют единственного владельца в базовом скилле. В обычной локальной задаче root вправе работать сам; активный dispatcher_only отменяет такой fallback, включая финальную проверку и восстановление.

Decomposer оформляет [назначения](../../codex-orchestration-pact/references/templates/task.md), граф и бюджет из действующего разрешения. Scout собирает факты; analyst разрешает неопределённость; architect выбирает решение; developer/mechanical реализуют; reviewer независимо проверяет назначение; integration_reviewer проверяет уникальные связи и полноту. Quality_owner ведёт только одну фазу качества и назначенные реестры, без реализации и независимой самоприёмки. Все роли пишут собственный отчёт; у аналитических/проверяющих ролей предметный write-set пуст. У общего изменяемого индекса/реестра один владелец. Роли не делегируют; нужный дополнительный вход передают предусмотренному владельцу через root.

Перед запуском установи фактические права, инструменты, источник настройки модели/reasoning: поддерживаемый вызов, проектный профиль либо документированное наследование. Запрошенное и наблюдаемое значения различай; универсальные профили их не фиксируют. Настройка не доказывает загрузку или фактическую sandbox. При недоступной роли/записи один раз уточни файловый контракт, затем точный блокер; предметный root не является заменой.

## Route: структурная форма

Следующий YAML-блок — канонический template `route.yaml`. Он показывает форму, а не существующее принятое исполнение. Предметные решения и команды находятся в назначениях. `version` — 1, `route_revision` — неотрицательное целое, bool не является целым. ID уникальны, роли реально доступны. `dependencies` — ID существующих назначений. `allowed_transitions` содержит точные переходы; только они разрешены отправителю.

```yaml
version: 1
route_revision: 1
assignments:
  - id: A01
    role: developer
    assignment_path: assignments/A01.yaml
    dependencies: []
    allowed_transitions:
      - action: review
        role: reviewer
        assignment_id: R-A01
        assignment_path: assignments/R-A01.yaml
        input_paths: [goal.md, reports/A01.yaml]
    write_set: []
    shared_resources: []
  - id: R-A01
    role: reviewer
    assignment_path: assignments/R-A01.yaml
    dependencies: [A01]
    allowed_transitions: []
    write_set: []
    shared_resources: []
acceptance:
  reviewer_assignment_id: null
  report_path: null
  route_revision: null
```

`acceptance` заполняется только после независимого review данной ревизии: существующие ID reviewer и путь его отчёта, та же route_revision. До приёмки null допустим для bootstrap/проверки плана, но не продуктивных назначений. Root сверяет runtime-отправителя и связь с назначением reviewer; самооценка decomposer не принимает граф. Реальный граф заранее включает plan-review, correction/revalidation и терминальные переходы, нужные цели. Пустой список переходов примера не разрешает root их сочинить.

Изменение графа, критериев, проверок или write-set оформляет decomposer; новая ревизия проходит независимую приёмку до исполнения. Изменение бизнес-смысла требует пользователя. Предметный владелец устанавливает затронутые прямые и транзитивные результаты; несвязанные сохраняются. Старое доказательство остаётся в истории и не заменяет актуальную приёмку.

## Budget: фиксация разрешения

Канонический template `budget.yaml` хранится здесь, отдельный исполнитель бюджета не вводится. Decomposer заполняет известные лимиты, источник разрешения и условия остановки; неизвестные лимиты — null, а не бесконечное разрешение.

```yaml
max_batches: null
time: null
resources: null
await_user: []
blocked: []
handoff: []
permission_source: goal.md
```

`max_batches` — положительное целое либо null; `time` и `resources` — явно описанные лимиты либо null, три списка — конкретные условия. Для кампании качества без заданной длительности устанавливается `max_batches: 1`: одна принятая партия и контрольная точка. Это default кампании, не лимит bootstrap-рефакторинга, числа дефектных циклов или разрешение платных evals. Несколько разрешённых партий выбирает quality_owner в пределах бюджета. Исчерпание сохраняет принятые результаты и непроверенное, не даёт approved и не означает совершенство продукта.

## Envelope и допустимый переход

[Envelope](templates/envelope.yaml) имеет только `status`, `artifact`, `assignment_id`, `route_revision`, `next_transition`, `decision_question`; это не полный отчёт. `status` совпадает с [каноническим отчётом](../../codex-orchestration-pact/references/templates/report.md). Root проверяет структуру, существование artifact, безопасные пути, отправителя по runtime_handle, его ID/роль/ревизию и принятое ребро, не читая предметный отчёт. Следующая роль проверяет совпадение статуса и содержание. Изображения, evidence, логи и diff не входят в извещение. Обычно envelope укладывается в 12 строк; большой список входов заменяется ссылкой на существующий манифест, читаемый следующей ролью.

`action`: `dispatch | review | fix | integrate | revalidate | await_user | finish`.

- `dispatch/review/fix/integrate/revalidate` требуют `role`, `assignment_id`, `assignment_path`, `input_paths`. Назначение уже существует, ID/роль совпадают с route, зависимости удовлетворены, ресурсы свободны. Неизвестный ID не считается готовым назначением.
- `await_user` — терминальный предусмотренный переход с `status: blocked`, существующим `question_path`; `decision_question` содержит тот же путь. Роль готовит файл, root передаёт дословно, ответ сохраняет как новую инструкцию. При обычном переходе `decision_question: null`.
- `finish` — предусмотренный терминальный переход, основанный на независимой приёмке по route. Он не обязан изображать запуск роли. Root передаёт подготовленный предметной ролью короткий итог и ссылки, без чтения/пересказа полного отчёта. Приёмка партии и завершение кампании различаются.
- `next_transition: null` допускается у envelope только при `blocked` и точном отсутствии безопасного перехода. Root его не придумывает.

Completed реализации ведёт к reviewer; принятые части с уникальными связями — к integration_reviewer. Провал review ведёт по заранее подготовленному диагностическому/корректирующему назначению, затем к decomposer при изменении графа. Reviewer не исправляет принимаемое. Ошибка формы/отсутствующий путь получает один возврат отправителю только на исправление сериализации; повтор блокирует ветвь. Это не лимит исправлений реализации.

## Компактное состояние и повторы

[State template](templates/state.yaml) задаёт обязательные верхние поля. `mode` всегда dispatcher_only; `phase` описывает фазу процесса, `decision.status` — `none | await_user`, `question_path` null либо существующий путь вопроса. `route_path: null` допустим только в bootstrap до принятого графа; у обычного состояния маршрут существует и согласован с активными назначениями. `version/route_revision` — целые, не bool. Nullable пути и last_checkpoint остаются null при неизвестности; last_checkpoint при наличии — строка времени наблюдённого снимка.

Элемент `active_assignments` имеет `id`, `role`, `status`, `assignment_path`, `artifact`, `envelope`, `route_revision`, `runtime_handle` (строка либо null). Пути artifact/envelope могут быть null до получения результата; заполненные ссылки существуют. Статусы: `pending | ready | running | completed | approved | blocked | needs_revalidation | cancelled`. Ready всегда имеет существующее исполнимое назначение принятой ревизии. Split_required/baseline_failure полного отчёта отображаются как blocked со ссылкой на точный отчёт, не становятся новыми статусами state.

Только root пишет state: временный файл рядом → полная запись → rename/replace после запуска, ответа, смены перехода. Незавершённый временный файл не checkpoint. В оперативном состоянии лишь активные назначения/текущая партия; история по accepted_index_path не читается root каждый ход и не дублирует изменяемые оперативные статусы.

Идемпотентность: assignment_id + route_revision + runtime_handle и сохранённый envelope различают попытку и повтор события. Идентичное событие не запускает действие повторно. Новая попытка получает новый runtime_handle/явно оформленное назначение; до повтора побочного действия роль устанавливает, произошло ли оно. Поздний ответ старой ревизии сохраняется как доказательство, не меняя текущего статуса. Безопасное чтение повторяется один раз, затем существующий эквивалент либо точная недоступность. Это процедурная защита, не техническое exactly-once.

## Пути и ресурсы

В concrete task task_root — явно установленный локальный корень. Отчёт/вопрос/назначение/state/route/envelope и входные ссылки задачи относительны ему: абсолютный путь и `..` запрещены. Проверь реальную цель через resolve и containment, symlink/reparse escape, отсутствующего родителя и петлю ссылок; ошибка разрешения не разрешает запись. Существующие входы/переходы проверяются до выдачи envelope. Цель будущего отчёта разрешается до запуска, её безопасный родитель проверяется заранее. Исходный write-set относится к явно названному Git-контексту и точному разрешению, а не обязан лежать под task_root.

Template проверяется по форме/типам без существования демонстрационных путей; concrete дополнительно требует существование, containment, согласованные ID/роли/ревизии и route. Ни одна структурная проверка не исполняет команды из документов и не доказывает поведение клиента.

Непересекающихся write-set недостаточно: учитывай общий Git-индекс, БД, порты, серверы, тестовые данные и состояние. Root сверяет структурные ресурсы графа, конфликт диагностирует владелец. workspace-write — процедурное право, не техническая изоляция папки. Сохраняй чужие изменения; роли учитывают новые/удалённые файлы и отдельные игнорируемые артефакты в манифестах, а не только git diff. Для устойчивого снимка и weak running используй [continuity](continuity.md).
