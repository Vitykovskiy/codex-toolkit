# Strict dispatcher mode

Apply this boundary only to an explicitly selected `dispatcher_only` workflow or active strict continuation under the [mode rule](../../codex-orchestration-pact/SKILL.md#dispatcher-invariant). At every launch, retry, review and resume, root only dispatches permitted roles and records process metadata. It reads no subject source, assignment, report, excerpt, summary, diff or handoff, including through deliberate tool reads or inherited peer context, and neither reformulates the request nor changes its role. Progress assessment, recovery and missing capabilities do not waive the boundary.

Launch with the role and basic instruction, unchanged original user text or exact reference, task root, assignment ID/attempt and dependency references. The subject owner locates primary sources and required predecessor reports itself, checks their currency, formulates and records its working task, then performs the assigned decision, change or independent review. The working formulation never replaces the original request for the next agent.

Preserve original wording, language, order, numbers and qualifiers; later user corrections remain ordered separate sources. When durable access is needed, the first subject owner preserves the received text in its existing authorized source/result artifact and returns its reference. Root does not reconstruct, select or translate requirements. Missing or ambiguous required evidence blocks dependent work; file availability may be checked as metadata only.

Previously loaded sources, native memory or automatic result delivery do not themselves require a new session or permission. Continue using permitted process fields and source references; subject owners still perform required primary-source and currency checks. Do not claim that instructions erase or technically isolate context.

A subject owner prepares needed assignment content, graph, write-set and route revision. Root receives only routing fields from the [envelope](templates/envelope.md); the next agent opens the referenced assignment. A ready specification goes directly to its executor. Architect handles material technical decisions; decomposer prepares missing execution dependencies and ownership under [Parallel execution](../../codex-orchestration-pact/references/parallel-execution.md), without becoming a mandatory relay. Fixes and implementation integration stay with their developer; independent acceptance stays with the reviewer. Use integration_reviewer instead of ordinary review only for a named compatibility or security criterion; one sufficient packet review can accept several results.

Root validates envelope shape, runtime sender, assignment ID/attempt, revision, path safety and permitted transitions from process metadata. The reviewer verifies full reports, evidence, source revision and envelope/report correlation. A path-only next transition requires a routing descriptor from its subject owner; root never opens the assignment to infer a role or instruction. Unsafe, ambiguous or stale metadata yields an exact checkpoint for affected work; independent ready work may continue.

Root maintains the ready/waiting queue in its existing [state](templates/state.md). Before each launch it records assignment identity, plan/input revision, bound dependency snapshots, resource reservations and known applicable limits, then attaches the native handle. Apply the shared parallel rule for actual capacity, conflicting resources, completion gates and cancellation; no fixed writer cap or mandatory budget agreement is introduced. Use native completion or blocking waits, unlock each successor when its own gates pass, and process duplicate events only once. Subject owners assess source or dependency changes and return affected assignment IDs and revised descriptors; root never computes subject impact.

Apply the common [progress and waiting rule](../../codex-orchestration-pact/SKILL.md#progress-and-efficiency) and the strict fields below. Missing delegation, report storage, reference-only delivery or a safe transition stays blocked without a technical or report-reading fallback.

## Progress and efficiency

Show approximate task completion in meaningful updates, with the current stage and next transition. Estimate from confirmed outcomes, including required implementation, independent acceptance and delivery. Calls, elapsed time, documents and repeated checks do not earn completion; 100% requires every required stage, including requested publication.

A stream (`поток`) is one executable subtask from its first launch through its own accepted result and required delivery. The plan owner assigns a stable `stream_id`; all role assignments for that subtask, including review, corrections and resume, keep it. For nested decomposition, count launched child subtasks and retain their parent as an aggregation group. Several scouts for one subtask occupy one stream.

Every meaningful strict progress update includes approximate whole-task completion, active stream count, and each active stream's completion and stage or waiting reason, identified by `stream_id`. Count each launched, unfinished stream once through handoff, queued review, corrections, pauses and blockers. Preserve its latest valid progress until its designated owner confirms all completion criteria, including acceptance and delivery. Unlaunched subtasks remain pending. Native assignment completion advances a stage; it does not close the whole stream. Unknown lifecycle or mapping remains unknown pending the existing owner's process update.

Each stream advances through its own work, independent review and corrections as soon as its dependencies and capacity permit under [Parallel execution](../../codex-orchestration-pact/references/parallel-execution.md). The plan owner prepares that review route within the stream. Shared integration criteria have explicit source-backed dependencies and a scoped integration route; unrelated streams continue. Name the reason and next transition for a resource or dependency wait.

The existing plan owner defines stages, weights and confirmation basis and supplies task-level `completion`: `plan_revision`, `confirmed_weight` and positive `total_weight`, with `0 <= confirmed_weight <= total_weight`. Root uses their ratio and replaces the previous aggregate; it does not sum receipts or average agent percentages. Evidence and stage criteria stay with subject owners and reviewers. Executor completion does not confirm independent acceptance.

Each stream has one designated progress owner supplying `stream_completion` under the same confirmed-outcome, weight and revision rules for its full scope. Derive stream percentages from their own totals and whole-task progress from the task-wide aggregate. Preserve both through role changes and resume; mark unavailable values unknown. The existing [envelope](templates/envelope.md) and [state](templates/state.md) carry these fields.

Keep the denominator stable within a plan revision. A material scope or plan change needs a new owner-issued revision and recomputation preserving valid outcomes; explain a decrease as a revision. Reject stale or conflicting aggregates. Request only the missing process metadata when current totals are unavailable.

At normal checkpoints, subject owners compare work with original goals and remaining criteria and return any `process_signal`: `on_track`, `stalled`, `repeated_action`, `excessive_verification`, `plan_drift`, `goal_drift`, or `unknown`. Signal material problems promptly. Diagnoses, plan content and check justifications stay in owner artifacts; root receives only signals, identities, completion fields and routing references.

On a stall, repetition, excessive verification or drift, root redirects the existing owner using source references and process fields. Two consecutive substantive receipts for the same unresolved work without confirmed progress trigger the same correction; duplicate notifications do not count. Pause affected repetition while independent work continues. Root neither chooses a technical strategy nor reads subject artifacts. The decision owner retains accepted work and returns one bounded next action, expected result, stopping condition and updated transition. Root checks the next meaningful checkpoint for confirmed movement.
