# Контрольная точка и возобновление dispatcher_only

Применяй при передаче незавершённого процесса, смене сессии или приближении предела контекста. Это обязательное дополнение [ядра long](../SKILL.md) использует его единый `state`; отдельный handoff-снимок не требуется. Общие критерии снимка и дефектной приёмки остаются в [базовом протоколе](../../codex-orchestration-pact/references/complex-task-orchestration.md); их широкое чтение доказательств root здесь не применяется. Передача не отменяет dispatcher_only и не заменяет доступное завершение.

## Создание

1. Root прекращает новые назначения, получает фактическое состояние доступным ожиданием/остановкой, сохраняет runtime_handle и незавершённые процессы. Средство остановки, отдельный Git-контекст и успешное ожидание нельзя предполагать. Если устойчивость не подтверждена, снимок unstable; затронутые назначения needs_revalidation по сведениям владельца. Неполный снимок partial. Оба не называются complete.
2. Root механически фиксирует для каждого реально обнаруженного Git-контекста локальный корень, ветку/detached, HEAD, staged/unstaged/untracked-состояние и отпечатки рабочего/индексного diff. Абсолютный корень допустим в локальном снимке; универсальные инструкции остаются переносимыми. Root не анализирует содержимое diff.
3. Предметные роли сохраняют манифесты существенных входов, результатов, новых файлов, удалений и данных вне отслеживаемого diff. Каждый элемент содержит контекст, путь, метод, значение либо состояние отсутствия. Игнорируемые артефакты перечисляют отдельно. Изменение сценария, файла, конфигурации или снимка требует оценки влияния владельцем, а не автоматической отмены всех результатов root.
4. В едином state сохрани goal_path, короткий журнал решений по пути, текущие envelope, Git-снимок, ссылки на манифесты и ровно один следующий допустимый переход. Не копируй полные отчёты, изображения и историю. Совместимый handoff допустим как ссылка или представление этого state, но не является вторым обязательным снимком. Root записывает своё компактное состояние; полный отчёт создаёт назначенная роль. При отсутствии безопасного перехода blocked и null фиксируют блокер, а не выдуманный запуск.
5. Запиши state/checkpoint атомарно через временный файл в том же каталоге и rename/replace; укажи partial/unstable/complete по фактам и обнови checkpoint_path/last_checkpoint. Временный файл не считается контрольной точкой. Наблюдённые процессы, неизвестности и первое действие должны позволять восстановление без воспоминаний прежнего root.

## Возобновление

1. Root читает применимый AGENTS, ядро long, goal, state и envelope следующего назначения; совместимый handoff читает только если он был сохранён как ссылка/представление state. Маршрут и бюджет — для механической сверки перехода. При нескольких активных задачах нужен точный ID/путь; выбор по догадке запрещён. Полные отчёты/манифесты/предметные доказательства читает только назначенная профильная роль.
2. Сохрани dispatcher_only. Повторно обнаружь доступные Git-контексты, индекс и процессы. Прежний running — слабый факт: проверь реальную связь runtime_handle с текущей сессией/процессом. Нет наблюдаемой связи — needs_revalidation, а не автоматический повтор запуска.
3. Различие Git-снимка направь по предусмотренной узкой разведке/review. Владелец сравнивает отпечатки, устанавливает существенные прямые/транзитивные зависимости и перепроверяет затронутые результаты; несвязанные сохраняются. Root не исследует diff и не сбрасывает все одобрения.
4. Для partial/unstable назначенная роль восстанавливает недостающее по существующим файлам, сохраняет неизвестности и готовый переход. Неполнота не становится done. Отсутствующий безопасный маршрут — точный blocker; root не создаёт предметные назначения сам.
5. До возобновления проверь существующее назначение, зависимости, ресурсы, полномочия и известный расход по [dispatcher-mode](dispatcher-mode.md). Сохрани накопительный расход, счётчики, приращения с их устойчивыми ключами и незавершённые резервы из state; смена сессии, стратегии или партии не создаёт новый бюджет и не обнуляет эти значения. Перед новым запуском root один раз сверяет общий известный остаток и все открытые резервы для всего параллельного набора; неизвестное остаётся `unknown`. Сопоставь ID, попытку и runtime_handle с сохранённым извещением; повторное сообщение не повторяет побочное действие, поздний старый ответ остаётся историческим доказательством. Роль проверяет фактический исход прежнего действия перед новой попыткой.
6. Возобнови только готовый допустимый переход и атомарно обнови state. Перезапуск или новая сессия возможны только фактически доступным средством; запись state или совместимого handoff не доказывает запущенное продолжение. Финальный предметный вердикт готовит независимая роль; root передаёт подготовленный краткий текст/пути без чтения и пересказа полных отчётов.

Результат: компактный checkpoint или возобновлённое процессное состояние с точными ограничениями. Отдельно укажи структурную проверку, смысловую приёмку, загрузку клиентом, поведение двух сессий и эффективность. Статическая проверка шаблона не подтверждает действительную файловую передачу или exactly-once.
