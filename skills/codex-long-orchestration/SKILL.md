# Long orchestration

Use `dispatcher_only` only for an explicit strict dispatcher or a resumed strict workflow. It is not triggered by file count, a normal fix/review pair, two ordinary stages, or ordinary continuity between sessions.

This mode follows the [general rule for verification means](../codex-orchestration-pact/SKILL.md#general-rule-for-verification-means). Keep generated process prose in concise English, with exact source wording and all machine fields unchanged.

Root owns organization: it starts prepared assignments, assesses progress from necessary result parts, records transitions, changes the order of independent work, and splits an oversized package while preserving the user goal and constraints. It does not replace a subject role for a technical decision or implementation, and does not independently approve its own work. Subject roles own the decision, write-set, implementation, permitted existing checks, and full report.

The architect may prepare the graph and write-set; do not require a decomposer before or after it. For a ready user specification root may mechanically fill an assignment with its literal goal, scope, and checks. An assignment preserves the user's explicit execution and verification limits. Excluded checks remain unrun; required independent approval is not fabricated when its evidence is absent. A completed implementation receives one independent review; use one packet review for multiple completed assignments. Preserve accepted evidence for unchanged work and recheck the fix and its dependencies only.

Roles atomically write their own full reports and return a compact envelope. Root keeps one current state and resumes the first incomplete action without reissuing accepted work. Missing delegation, report storage, or a safe transition is a precise checkpoint, not permission for root to become the technical fallback. After two attempts without confirmed progress, root changes organization rather than repeats the same assignment.
