# Orchestration pact

Use this pact for requested orchestration or actual coordination. A ready local edit can be performed directly. Select the route once; revise it only for a material change in scope, evidence or responsibility.

## Dispatcher invariant

**Critical process warning — mandatory at every stage.** A dispatcher-mediated retelling starts cumulative task degradation: each relay can amplify an earlier omission or interpretation. Preserve the original request unchanged and let each subject agent formulate and record its own working task from primary sources. Never waive this invariant for convenience, compression, progress assessment, recovery, or a missing capability.

This boundary applies whenever an orchestrator acts as a dispatcher, in ordinary and strict workflows. A root doing an authorized direct task is its subject owner, not a dispatcher; dispatch cannot silently switch into direct execution. The dispatcher neither expands nor narrows its role.

The dispatcher launches the next permitted subject role, waits through native mechanisms, records compact process metadata, and uses those fields to report completion and route process corrections under [Progress and efficiency](#progress-and-efficiency). Its launch contains the role and basic role instruction, task/assignment ID, attempt, original user text verbatim or its exact source reference, task root and dependency identifiers/references. Preserve user wording, language, order, numbers and qualifiers at every launch, retry, review and resume. Forward a later user correction verbatim as an additional source; it does not authorize rewriting the earlier source. Use an original request reference rather than selecting, translating, summarizing or extracting requirements. Never replace the task with a prior agent's formulation.

The dispatcher reads no subject files or agent-authored artifacts: no source code, source documents, assignments, plans, findings, full reports, excerpts, summaries, diffs or handoffs. This includes organizational or progress-related reading and indirect loading through tool output, inherited peer context or an agent message. Keep only the current routing instructions, verbatim user input/source references, native handles, identifiers, process status and the dispatcher's own compact state. Receive only a routing receipt/envelope, never a subject result; validate its process fields and runtime sender without opening its artifact. File availability may be checked as metadata without loading content. Subject evidence, report/envelope consistency and source currency are checked by the assigned subject owner or independent reviewer.

Each subject agent independently locates and reads the original request, applicable project instructions and required predecessor artifacts before dependent work. Start from task root, task/assignment IDs and source references; use the existing assignment dependencies and report locations to find required reports yourself. Check identity, attempt, goal version, relevant source currency and required snapshot; keep an unavailable or ambiguous dependency blocked rather than reconstructing it from a relay. Record your own working task, scope, criteria, limits and primary source references in the existing assignment/result artifact or ordinary working context. Keep that formulation distinct from the authoritative request; the next agent repeats this grounding independently. A scout finds source facts and rules; an executor finds dependent reports and actual work files; a reviewer finds original criteria and foreign evidence.

When later roles need a durable original, the first subject owner preserves the received user text verbatim in its existing authorized source/result artifact and returns only its reference; later corrections remain ordered separate sources. No dispatcher reconstruction is involved.

A subject owner prepares any required assignment, dependency, write-set or route revision and makes dependency artifacts accessible to later owners. The dispatcher forwards only their identifiers/references and permitted routing fields. It does not choose a subject scope, split a package, select requirements, invent criteria, assess subject evidence or rewrite a prepared assignment. Completion arithmetic uses owner-confirmed process fields, not the dispatcher's interpretation of work. A role change or stagnation uses the existing decision owner and the same original sources; it is not permission for the dispatcher to become that owner. A ready specification still goes directly to its executor, without an extra planning relay.

Ordinary direct results may remain inline. In a dispatched workflow, subject results needed by another role are kept in the existing accessible task/assignment/report location, and the dispatcher receives only process metadata and artifact references. This does not activate strict mode or require its full schema. Strict dispatch uses role-owned canonical reports and envelopes. Without shared artifact access or a channel that keeps subject content out of dispatcher context, record the exact capability blocker; do not read or relay report text as a fallback. No new transport, registry or automation is introduced.

## General rule for verification means

Subject roles implement the requested result; the dispatcher only coordinates their launches. Creating new unit, integration or other tests, validators, check scripts, or other auxiliary automation to verify implementation or maintain the process is outside orchestration. Create such means only on the user's separate direct request to create them.

An assignment, another agent's plan, or the expected usefulness of a means does not replace that request. A temporary script, one-off checking code, and a new test case in an existing test file are also new verification means. Do not rewrite existing tests around an implementation to obtain a passing result. Product code requested by the user remains permitted implementation; a product fix or improvement alone is not an authorization to build verification infrastructure.

Existing checks, normal code reading, and independent review remain permitted within the task. Run existing permitted checks when relevant, and report unrun work honestly. Manual checking is permitted, but do not introduce a mandatory manual acceptance, user confirmation, or universal browser stage. Preserve checks explicitly required by the user. Source review is not runtime observation.

Choose checks in proportion to the task, affected contracts and remaining risk. Each additional or repeated check must address a named uncovered criterion, a relevant changed input, or an inconclusive result whose cause can now be resolved. Reuse current evidence and stop optional verification once it supports the required decision; check count and repeated successful runs are not progress. Preserve required gates and independent acceptance rather than replacing them with a numerical check limit.

## Project requirements

Before a subject decision or change that depends on them, read the applicable original user requirements, project rules and skill limits: DoD, code style and placement, architecture and dependencies, product/API/data/UI contracts, and relevant security, documentation, verification and release conditions. This applies to every subject owner, including direct work without delegation. A dispatcher follows the [dispatcher invariant](#dispatcher-invariant) and leaves subject reading to those owners. Reading this section does not activate orchestration, strict mode or another approval stage. Requirements must be obtained and applied; a separate scout run is not required by default.

Reuse requirements already read and still current for the affected scope. If rules are unknown, scattered across sources or span multiple areas in an orchestrated task, the orchestrator assigns their collection to the existing `scout`, combining it with an ongoing scout assignment when possible. Launch the scout with the original task verbatim or its exact reference and the task identifiers; the scout determines applicable scope and limits from those sources. Complete the relevant collection before dependent analysis, design or changes; independent work may continue. For a simple local edit, its owner reads applicable rules directly. A pure lookup of one fact that does not prepare subject work retains the narrow scout scope. A developer does not spawn agents: read one available source directly or ask the orchestrator for additional investigation.

Start from the original request and applicable `AGENTS.md` / `AGENTS.override.md`, including instructions for affected directories, following their actual discovery and precedence rather than assuming both files apply. Navigate the project's README, contributing guidance, documentation, accepted decisions and configuration by relevance; project-specific names and paths are not universal toolkit requirements. Read the relevant sections, conditions, exceptions and linked normative sources needed to understand them, without loading unrelated documentation. For each applicable rule, retain its wording or an accurate sufficient excerpt, source and section or lines, scope and conditions; preserve force, exceptions, numbers and identifiers. Separate recommendations and history from current rules. Existing code is implementation evidence, not automatic proof of a rule; an internet recommendation is not a project mandate. Scout web searches retain their confidentiality and non-execution limits.

The scout records the inspected scope, applicable rules and sources, material unread sources, conflicts and unknowns in its role-owned result. “Not found in the inspected scope” does not prove global absence. Each dependent owner finds that result through the task identifiers and dependencies, reads the relevant rules and follows their primary sources. Retain source sections, scope, conditions, authorization limits, gaps and known revision in the existing result fields; this is not a new machine schema. The dispatcher does not read, filter, select or redistribute the rules. A reference or a file's existence does not establish that its recipient read it.

Analysts resolve their uncertainty against original rules. Architects and explicitly requested decomposers prepare source-backed decisions and assignments within existing authority. Developers and mechanical owners read source rules, work files and dependent reports themselves. Reviewers independently locate the original goal, current applicable rules, actual changes and foreign evidence; the developer's formulation is not their criteria source. `reviewer_fast` retains its literal-only scope. Quality owners use project rules alongside confirmed charter/preferences. Corresponding Astra profiles retain their existing invocation conditions.

Original project documents and the user request remain authoritative; each agent's formulation and extracted rules are working context, not a replacement rulebook. On resume or replacement, the dispatcher forwards unchanged original references, task/assignment IDs and dependencies; the owner locates and reads the material itself. Reuse current extracted rules without a scout rerun just because a session changed. A changed source, scope or uncommitted edit requires the subject owner to recheck the affected subset and identify dependent results; unchanged HEAD alone does not establish currency. Keep unrelated accepted work and use existing state, versions and diff without new hashers or registries.

Resolve instruction conflicts by established precedence and scope. Refer unresolved subject ambiguity to the appropriate analyst or architect and a necessary user decision through the orchestrator; pause only dependent work. If a required criterion cannot be evidenced under current execution limits, name the source, conflict and missing evidence without claiming completion. Collecting a DoD does not authorize new tests, validators, check scripts or process automation: the [general rule for verification means](#general-rule-for-verification-means) still applies.

### Project knowledge sources

When collecting context, identify any project-declared knowledge store and its available authorized read interface. A vector database may help find semantically related rules, decisions and usage across different wording. Use it when it can close a concrete context gap; reuse already grounded current context rather than making retrieval a mandatory stage for every edit.

Combine focused semantic queries with exact identifiers and direct file/source search. Scope queries and available filters to the relevant project, component and source revision; retrieve a small useful set, remove duplicates and expand only for a remaining question. Search ranking is a discovery aid, not authority or proof of exhaustive coverage; an empty result does not establish absence or find every code reference.

Before applying a hit, open its current primary source and enough surrounding context to establish the rule, scope and exceptions. Retain source URI/path, section or chunk locator, and known source revision/index freshness in the existing result alongside material gaps. Compare against current source content, including relevant uncommitted changes; index timestamps or matching HEAD alone do not prove currency. Source rules and established precedence govern retrieved text. A chunk, generated summary or similarity score does not replace the source or grant execution authority.

Use direct source/keyword search when the store is unavailable, stale or insufficient, and report the affected gap; pause dependent work only when a necessary source remains inaccessible. Query only through existing authorized means and keep confidential query content within approved data boundaries. Retrieval does not authorize setup, installation, database writes, bulk embedding jobs or reindexing. Changed sources require rechecking affected evidence, not rebuilding the entire knowledge store as part of context collection.

The scout uses this route for applicable rules and source discovery. The analyst and architect use it for a material unknown or prior decision; the developer for relevant implementation patterns and constraints; reviewer and integration_reviewer for independently locating missed or cross-part requirements; quality_owner for a gap in campaign context. Their Astra variants follow the same subject rules under their existing invocation conditions. These roles already follow Project requirements; extra retrieval is needed only for a concrete gap. Decomposer, mechanical and reviewer_fast keep their existing direct-source scope, and a dispatcher performs no knowledge retrieval.

## Portable route table

| Work | Route |
|---|---|
| Ready text, instruction or mechanical configuration edit | One owner, including the current root in ordinary mode. Independent review only when the task contract or semantic risk requires it and the user permits it. |
| Connected behaviour change | One `developer`, then one independent `reviewer`. The developer resolves ordinary local implementation questions. |
| Truly independent outcomes | Coarse assignments by responsibility, at most two simultaneous writers, then one sufficient batch review. |
| Material technical decision uncertainty | One `architect` consultation that may also prepare executable assignments and write-sets. |
| A specific unanswered source or requirements question | Direct relevant reading, or one `scout` / `analyst` assignment when delegated investigation is needed. |
| Explicit strict request or continuation of active strict state | [Long orchestration](../codex-long-orchestration/SKILL.md) with role-owned reports and independent acceptance. |
| Explicit product-quality campaign | [Product quality](../codex-product-quality/SKILL.md) with its stated scope and stopping point. |

File count, a normal fix/review pair, broad wording, an iteration number, or persistence between sessions do not activate strict mode. Ordinary continuity needs the current goal, completed work, remaining work, constraints and next step in the existing state location. Strict mode remains for an explicitly requested route or active strict task. A ready specification does not need an analyst, architect or decomposer to restate it. `decomposer` remains an explicitly requested standalone or legacy-import capability, not a mandatory relay; an architect may prepare technical decomposition when needed.

## Scope and profiles

A subject-owned assignment records its source-grounded goal, scope, criteria, required evidence and execution limits under the [dispatcher invariant](#dispatcher-invariant). The dispatcher launch carries only the role, basic instruction, original text/reference and identifiers needed for the recipient to find its assignment and dependencies. Preserve profile boundaries; never inject a parent conversation or peer result into dispatcher context.

Use existing profiles with their configured model and reasoning values. `reviewer_fast` handles only provably literal non-semantic edits. `integration_reviewer` replaces ordinary review when a named security or cross-part criterion requires it. Astra profiles require a direct applicable user request. A retry, complexity or a child-created assignment does not supply authorization.

## Execution and acceptance

The dispatcher launches permitted stages in dependency order from the route table or a subject-prepared transition. Subject owners decide package scope, dependencies and any necessary revision within the original authorization. The dispatcher records receipt fields and native completion, not an assessment of report content. It neither becomes an executor nor grants independent approval. This boundary also applies outside `dispatcher_only`.

One sufficient independent review covers the requirements, implementation, related risks and relevant connections. Add another reviewer only for an explicitly named uncovered criterion. Return a defect to the same owner and reviewer; reread the changed evidence and affected dependencies, not the entire history. Apply [Progress and efficiency](#progress-and-efficiency) throughout active work and before a retry or extra verification pass. Use existing receipts and state, without new counters, KPI, logs or monitoring means.

Retain the existing six-key report and acceptance contract. Batch approval identifies every assignment, attempt, goal version and required snapshot. No self-approval, duplicate or stale acceptance, incomplete result, or missing required evidence is valid. A formatting correction to a report does not restart implementation or invalidate still-current evidence. A scope escape, missing required evidence, or stale acceptance remains a substantive review issue.

Ordinary direct work uses inline results unless a file is assigned. Dispatched work follows the reference-only handoff in the dispatcher invariant; strict work writes the canonical report atomically and returns only its envelope. Wait through native completion or blocking tools. Reuse a relevant owner context for a narrow fix; create a new context for a different responsibility. Do not create agents just to summarize, translate, poll or repackage another agent's result.

## Progress and efficiency

Show approximate task completion in meaningful user-facing updates, for example `≈40%`, followed by the current process stage and next transition. Estimate from confirmed outcomes of the current plan, with coarse weights for materially different stages. Include required implementation, independent acceptance and delivery stages in the denominator; time spent, calls, documents produced and repeated checks do not earn completion by themselves. Use 100% only after every required stage is confirmed, including requested publication.

The existing plan owner defines the stages, weights and confirmation basis in its working context or assigned artifact; a simple task uses its current executor without an extra planning role. In dispatched work that owner supplies task-level `completion` metadata: `plan_revision`, `confirmed_weight` and positive `total_weight`, with `0 <= confirmed_weight <= total_weight`. Root derives the approximate percentage from their ratio and replaces the previous aggregate rather than summing receipts or averaging agent percentages. Subject evidence and stage criteria stay in owner artifacts and are checked by the appropriate reviewer. An executor's completion does not confirm an independent acceptance stage.

Keep the denominator stable within a plan revision. A material scope or plan change requires the owner to issue a new revision and recompute the estimate, preserving still-valid outcomes; explain a resulting decrease as a plan revision. Reject stale or conflicting aggregates as current progress. If current totals are unavailable, mark the percentage unknown and request the smallest missing process update from the owner, rather than inventing a value. Ordinary work uses compact receipts and existing state; only strict work requires the [envelope](../codex-long-orchestration/references/templates/envelope.md) and [state](../codex-long-orchestration/references/templates/state.md) formats.

During active work, each subject owner compares the next action with the original goal, current plan and remaining criteria. At normal checkpoints report confirmed progress and any `process_signal`: `on_track`, `stalled`, `repeated_action`, `excessive_verification`, `plan_drift`, `goal_drift`, or `unknown`. Signal a material problem promptly, before completion. Keep diagnoses, plan content and check justifications in the subject artifact; root receives only the signal, identities, completion fields and routing references. Use existing native events and meaningful checkpoints, not a polling or reporting loop. If an expected checkpoint is materially missed, root requests one process update from the active owner; elapsed time alone does not prove a stall.

On suspected looping, a stall, excessive verification or plan/goal drift, root redirects the active owner through a native message or the existing permitted decision-owner transition, using original source references and process fields only. Pause the affected repeat or dependent launch as needed; independent useful work may continue. After two consecutive receipts for the same unresolved work without confirmed progress, invoke that correction even if no explicit signal arrived; duplicate notifications do not count as another attempt. Root does not wait for formal failure, select a technical strategy or open subject artifacts.

The existing decision owner rechecks the original outcome and current plan, retains accepted work, and chooses one bounded next action with an expected result and stopping condition. Remove optional repetition or verification that no longer changes a decision, preserve required gates, and revise the plan only where evidence warrants it. Return the updated process fields and permitted next transition; root resumes that route and checks the next checkpoint for confirmed movement. An unresolved capability or user decision remains an exact blocker, not another identical attempt or an expanded assignment.

## Context

Subject owners read relevant files and ranges and expand when needed for correctness. Dispatchers follow the zero subject-reading boundary above. Reuse unchanged evidence without deleting its provenance. Load conditional references only when their conditions apply.

Keep stable instructions stable, with task-specific material after them where the client permits. Use existing provider caching only; add no cache service or unsupported settings. Native context inheritance and cache reuse are not proven by prompt wording. Missing usage remains unknown and does not trigger building a meter.
