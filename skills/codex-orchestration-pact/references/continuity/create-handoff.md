# Создание handoff

Handoff — проверяемая передача состояния оркестрации в новую сессию. Инструкция не опирается на память чата и не разрешает новые назначения, правки продукта, commit или push.

## Команда пользователя

> Контекст заполняется. Создай handoff оркестрации `<task-id>` по инструкции создания handoff из skill `codex-orchestration-pact`.

Идентификатор можно опустить, только если в `.codex/tmp/tasks/` однозначно есть одна активная задача. При нескольких задачах запроси точный идентификатор. Допустим прямой путь к нестандартному handoff.

## Порядок

1. Прекрати выдачу новых назначений. Текущую предметную работу не продолжай.
2. Прочитай `AGENTS.md`, обязательные пакты из него, [канонический пакт оркестрации](../complex-task-orchestration.md), эту инструкцию и доступные артефакты `.codex/tmp/tasks/<task-id>/`.
3. Запроси у каждого активного подагента короткий отчёт по каноническому `references/templates/report.md` и дождись финальных ответов. Root проверяет только обязательные поля, статусы и ссылки; предметную сверку маршрутизирует reviewer или integration_reviewer.
4. Подагентов, которые после ожидания продолжают работу или не вернули финальный отчёт, останови через `interrupt_agent`. Их неполученные, неполные или неподтверждённые результаты пометь `needs_revalidation`.
5. Повторно проверь список подагентов и подтверди, что выполняющих работу агентов не осталось. Git-снимки разрешено снимать только после этой проверки.
6. Замени любой оставшийся статус `running` на `needs_revalidation`: новая сессия не может доверять состоянию процесса прежней сессии.
7. Для основного проекта и вложенного репозитория `.codex` отдельно зафиксируй:
   - абсолютный корень, ветку и `HEAD`;
   - полный `git status --short`;
   - изменённые, удалённые и неотслеживаемые файлы;
   - отпечаток рабочего diff: `git diff --binary --no-ext-diff | git hash-object --stdin`;
   - отпечаток индекса: `git diff --cached --binary --no-ext-diff | git hash-object --stdin`;
   - отсутствие либо наличие staged-изменений; неотслеживаемые файлы покрываются отдельными отпечатками файлов.
8. Зафиксируй отпечатки всех файлов из разрешённых областей назначений, изменённых файлов и файлов, на которых основан статус `approved`. Для существующего файла используй `git hash-object -- <path>` из соответствующего репозитория; удалённый или отсутствующий файл запиши явно. Один отпечаток всегда относится к конкретному Git-контексту и пути.
9. Сверь и запиши текущую фазу, последний verdict, реестр артефактов и граф назначений: зависимости, роль, владелец, `frozen_write_set`, статус и отчёт. `approved` допустим только при независимом ревью и отпечатках принятого состояния.
10. Запиши выполненные проверки по одной команде: время, `execution_status`, `result`, краткое подтверждение или причину отсутствия результата. Изменение проверенного файла делает результат проверки устаревшим.
11. Сохрани дословные цель и ограничения, решение (если оно принималось), критерии приёмки, граф, `frozen_write_set`, распределение проверок, Decision Log, классификацию каждого замечания (`blocker` или `follow_up`), блокеры и последний verdict. Не восстанавливай отсутствующие факты по памяти или переписке.
12. Сформулируй ровно одно первое следующее действие: ID назначения, исполнитель, входы, разрешённые файлы, условия запуска и ожидаемый результат. Действие должно быть выполнимо новой сессией без знания чата.
13. Заполни канонический `references/templates/handoff.md`. Сначала создай полный временный файл рядом с целью, затем одним перемещением замени `.codex/tmp/tasks/<task-id>/handoff.md`. Частичный файл не оставляй.

## Результат пользователю

Верни только:

- путь к созданному handoff;
- статус активных назначений, переведённых в `needs_revalidation`;
- существенный блокер, если он есть;
- готовую команду:

> Продолжи оркестрацию `<task-id>` по инструкции возобновления из skill `codex-orchestration-pact`.
