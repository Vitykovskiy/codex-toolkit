# Оркестрация задач

Этот документ — единственный канонический маршрут оркестрации. Оркестрация включается только по прямому запросу пользователя, обязательному правилу или когда для результата нужны координированные независимые назначения. Число файлов, модулей или приложений само по себе не делает задачу `complex`.

## Роли и модели

Используй только зарегистрированные роли и их профили:

| Роль | Модель и уровень рассуждения | Назначение |
| --- | --- | --- |
| `scout` | `gpt-5.6-luna` / `low` | Факты о назначенной области. |
| `analyst` | `gpt-5.6-sol` / `medium` | Ответ на конкретную неопределённость требований или внешнего контекста. |
| `architect` | `gpt-5.6-sol` / `medium` | Технический выбор, границы и инварианты. |
| `decomposer` | `gpt-5.6-terra` / `low` | Независимые назначения, зависимости, `write-set` и проверки. |
| `mechanical` | `gpt-5.6-luna` / `low` | Однозначное изменение в известном `write-set`. |
| `developer` | `gpt-5.6-terra` / `medium` | Реализация атомарного назначения. |
| `reviewer` | `gpt-5.6-terra` / `medium` | Независимая приёмка любого назначения. |
| `integration_reviewer` | `gpt-5.6-terra` / `medium` | Полнота и уникальные связи нескольких принятых частей. |

`low` применяй для быстрых, однозначных действий; `medium` — по умолчанию для рассуждения и разработки. `high` не используй, пока измеримый выигрыш качества на репрезентативных задачах не подтвердит его необходимость.

## Общие инварианты

- Root — только диспетчер и конечный автомат: хранит дословные цель и ограничения, маршрут, статусы, зависимости и ссылки на артефакты. Предметные факты, решения, `write-set`, проверки, реализация и ревью принадлежат назначенным ролям.
- Состояние хранится в `.codex/tmp/tasks/<task-id>/`. Root передаёт путь к цели, а не её пересказ. Роль возвращает краткий отчёт с `status`, `changed_files`, `checks`, `result`, `risks`, `next_action`.
- Параллельно запускай все независимые назначения, которые допускает среда. Не параллель зависимые назначения, пересекающиеся `write-set` или конфликтующие ресурсы. Числового лимита параллельности нет.
- После принятия декомпозиции root замораживает цель, решение (если оно было), критерии, граф, `write-set` и проверки. Изменение за этими границами требует `split_required` или согласования пользователя.
- Reviewer классифицирует замечание как `blocker` только если оно нарушает замороженное назначение; всё остальное — `follow_up`. Допустим один исправляющий цикл и одно повторное ревью; затем только `approved` или `blocked`.
- `approved` сохраняется, пока не изменены результат назначения, его непосредственные входы, принятые критерии или решение. Найденная несвязанная работа его не отменяет.

## Компактный контракт отчёта

Каждая роль возвращает только шесть верхнеуровневых ключей: `status`, `changed_files`, `checks`, `result`, `risks`, `next_action`. `status` содержит ровно одно из значений `approved`, `blocked`, `split_required`, `baseline_failure`; `changed_files` — точный список собственных файлов или `[]`.

- Каждый элемент `checks` содержит `command`, `execution_status`, `result`; для `not_run` и `unable_to_verify` обязателен `reason`. Значения сохраняются: `execution_status` — `checked | not_run | unable_to_verify`, `result` — `passed | failed | null`.
- `result`, `risks` и `next_action` используют короткие именованные поля. Пустые вложенные секции не выводятся; шесть верхнеуровневых ключей сохраняются.
- `scout` возвращает `result.facts`: `path:line — \`symbol\` — факт`, затем `totals`.
- `mechanical` и `developer` возвращают `result.changes`: `path:line — изменение`; `changed_files` остаётся точным списком собственных файлов.
- `reviewer` возвращает `result.findings`: `path:line — blocker|follow_up — проблема — исправление`, затем `totals`; при отсутствии замечаний — `No issues.`
- `analyst`, `architect`, `decomposer` и `integration_reviewer` используют короткие именованные поля. Они сохраняют трассировку в `result`: `covered_goal_items`, `uncovered_goal_items`, `assumptions`, `scope_delta`, `contradictions`.
- `path:line` применяй только к утверждению о файле. Не выдумывай строки для решений, агрегированных итогов или источников без строк. Полные diff и длинные логи в отчёт не включай.

## Принцип минимального достаточного вмешательства

Вспомогательная проблема не становится новой задачей. Дополнительное изменение допустимо только когда оно одновременно является частью прямого результата пользователя, без него результат недостижим, это самый простой доступный способ и оно не создаёт новую постоянную обязанность проекта. Иначе роль фиксирует ограничение, использует существующее средство, ручную проверку или запрашивает расширение задачи.

Критерий готовности задаёт результат, а не разрешает создавать механизм проверки. Не создавай скрипт, линтер, валидатор, зависимость, перехватчик Git, задачу CI, абстракцию или средство резервного поведения, если это не прямой результат задачи или пользователь явно не согласовал расширение. Сбой skill, MCP или другого инструмента допускает один повтор; затем используй существующую альтернативу, ручную проверку либо верни `unable_to_verify` с причиной. Не пиши замену инструмента.

## Маршруты

| Этап | `simple` | `wide_mechanical` | `focused` | `complex` |
| --- | --- | --- | --- | --- |
| Когда | Однозначная локальная правка | Широкое, но однозначное изменение без выбора решения | Одна цель в ограниченной области | Есть архитектурное решение, высокая цена ошибки или зависимые области |
| Разведка | Нет | Нужные `scout` | Один `scout` | Независимые `scout` |
| Анализ | Нет | Нет | Только для конкретной неопределённости | Только для конкретной неопределённости |
| Архитектура | Нет | Нет | Только при выборе решения | Обязателен |
| Декомпозиция | Нет | Краткая | Только при нескольких назначениях | Обязательна |
| Реализация | `mechanical` | Параллельные `mechanical` | `developer` | Параллельные `developer` |
| Приёмка | `reviewer` | `reviewer` каждой части сразу после готовности | `reviewer` | `reviewer` каждой части сразу после готовности |
| Интеграция | Нет | `approved` отдельного `reviewer` после общей уникальной проверки | Нет | `integration_reviewer` |

Маршрут выбирается по сложности решения. Удаление одинакового контура из нескольких приложений — обычно `wide_mechanical`, а не `complex`.

## Выполнение и проверка

1. `scout` возвращает только факты: область, релевантные файлы и зависимости, связанные проверки, риски и полноту. При неполноте — `split_required` или `blocked`.
2. `analyst` запускается только после принятой разведки и только с исследовательским вопросом. Он возвращает требования, варианты, факты отдельно от допущений и критерии. Если analyst был назначен, `architect` получает только его `approved` отчёт.
3. `architect` запускается после `approved` scout и, если analyst был назначен, после его `approved`. Он выбирает решение только там, где нужен технический выбор, и возвращает границы, зависимости, контракты, инварианты и условия пересмотра. `decomposer` получает принятые входы маршрута и только `approved` решение, если `architect` запускался.
4. `decomposer` создаёт единый граф атомарных назначений: ID, цель, `write-set`, зависимости, критерий готовности, быстрая и полная проверки, возможность параллельного запуска. Если достаточного разбиения нет, роль возвращает точный запрос предыдущему владельцу.
5. Исполнитель меняет только назначенный `write-set`, решает прямую цель и выполняет быстрые целевые проверки. Он не строит новую инфраструктуру для проверки.
6. `reviewer` сначала проверяет границы и необоснованную сложность; лишняя постоянная инфраструктура — `blocker`. Затем он один раз выполняет полную приёмку назначения. Полные проверки не повторяют проверок исполнителя без причины.
7. `integration_reviewer` работает только после `approved` всех частей. Он проверяет полноту цели и уникальные межчастевые связи. Он не повторяет построчное ревью или полные проверки частей и не добавляет новые проверки.

Если общая проверка `wide_mechanical` падает, выполнивший её `reviewer` классифицирует замечание и передаёт его root. Если межчастевая проверка `complex` падает, это делает `integration_reviewer`. Root не диагностирует сбой сам; при необходимости `decomposer` создаёт отдельное назначение. Пересмотр архитектуры допустим только при физической невыполнимости критерия, подтверждённом нарушении публичного контракта, риске потери данных, безопасности или необратимого повреждения либо ложном входном факте.

## Завершение

Для `simple` и `focused` задача завершается после `approved` reviewer. Для `wide_mechanical` — после `approved` отдельного `reviewer`, выполнившего общую уникальную проверку. Для `complex` — после `approved` integration-reviewer. Финальный ответ кратко перечисляет результат, изменённые файлы, фактически выполненные проверки, риски и ручные действия.
