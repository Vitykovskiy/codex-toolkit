# Назначение

Decomposer заполняет точное назначение и последующие файлы до исполнения; root передаёт путь без реконструкции предметного тела. Следующая форма — template, демонстрационные пути не свидетельствуют о существовании файлов.

```yaml
assignment_id: A01
role: developer
dispatcher_mode: true
task_root: TASK_ROOT
route_revision: 1
goal_path: goal.md
input_paths: [goal.md]
write_set: []
artifact_path: reports/A01.yaml
criteria: ["Подтвердить критерии принятого назначения"]
checks: []
allowed_next_assignments: [assignments/R-A01.yaml]
```

В dispatcher-mode все поля обязательны: непустые ID/роль/пути, `dispatcher_mode: true`, целая актуальная `route_revision`, списки входов, точный write-set, критерии и назначенные проверки. `checks: []` допустим, только если командные проверки не требуются; ручные критерии всё равно проверяются. Зафиксируй зависимости, принятые входы, shared resources, наблюдённые права, Git-контекст исходных путей, быстрые команды с cwd и независимую проверку. Модель/reasoning приходят из поддерживаемой вызывающей настройки, а не универсального текста.

`task_root` — явно установленный локальный якорь; в конкретной задаче допустим абсолютный корень. Все ссылки на отчёт, вопрос, входы задачи и следующее назначение относительны ему и безопасны после разрешения ссылок. Исходный write-set относится к явно указанному рабочему контексту, не к task_root. `write_set: []` разрешает анализ; запись собственного `artifact_path` разрешается отдельно. Дополнительные артефакты должны быть явно назначены. Необходимый файл вне области требует пересмотра decomposer до записи.

Укажи допустимые следующие переходы из [принятого маршрута](../../../codex-long-orchestration/references/dispatcher-mode.md): action, роль, ID и существующий assignment_path с входами; предусмотренные коррекция/диагностика, review и терминальные исходы. Неизвестный ID или предложение в отчёте не становится готовым назначением. До принятого графа bootstrap-файлы создаются механически по явно заданному начальному маршруту.

Изменение цели, решения, критериев или write-set требует пересмотра и независимой приёмки ревизии. Изменение бизнес-смысла цели требует пользователя. Предметный владелец отмечает прямые и транзитивные результаты `needs_revalidation`; несвязанные сохраняются. Роль не делегирует, пишет полный [отчёт](report.md) и передаёт root только предусмотренное извещение.
