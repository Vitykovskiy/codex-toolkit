# Проверка runtime-артефактов

`tools/validate_toolkit.py --root .` сохраняет прежнюю структурную проверку toolkit. Необязательный отдельный режим `--task-root <путь> --manifest <относительный-путь>` читает только явно названный task root и YAML manifest версии 1. Он не разбирает Markdown-назначения, не пишет state, не запускает роли и не выдаёт semantic approval.

Manifest содержит `reports`: для каждого report — относительные `path` и `next_transition`, ожидаемые `assignment_id`, `attempt`, `goal_version` и, при наличии, относительный `envelope`. Для approved report `accepts` manifest содержит ожидаемый accepted-result triple: `assignment_id`, `attempt`, `goal_version`; любое несовпадение отклоняется, отсутствие этого trust input остаётся `not_verified`. Все пути обязаны оставаться внутри task root после resolve; traversal, отсутствующий путь и symlink escape — ошибки. Следующий transition должен существовать. Проверяются шесть ключей report, корреляция assignment, accepts и transition, а также correlation envelope/report.

Необязательный `owners` сопоставляет assignment ID с owner ID. Для `approved` report validator проверяет форму `accepts`; canonical envelope содержит ту же связь строкой `<assignment_id>/<attempt>` и добавляет `@<snapshot>` только при snapshot в report. Неверный ID, attempt или snapshot отклоняется. Когда обе стороны есть в supplied map, одинаковые owner ID отвергаются как self-approval. Нет owner map либо нужной записи — `not_verified`, не passed. Проверка owner map подтверждает только согласованность входа: profile text, parse YAML и разные имена не доказывают независимость роли, atomic write или runtime sender.

Envelope без blocker обязан иметь `finding_id`, `progress` и `no_progress` равными `null`. Blocker требует непустой finding ID и progress `confirmed`, `none` или `unknown`; `none` и `unknown` требуют непустые `no_progress.missing_input` и `no_progress.next_check`, а `confirmed` использует `no_progress: null`.
