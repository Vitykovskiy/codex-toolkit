# Project-local подключение

Это процедура **отдельного будущего запуска** в проекте-потребителе. Доработка toolkit ничего не устанавливает в Expressa, другие продукты или глобальные каталоги. Выполнение шагов ниже требует задания на конкретный проект; модельная проверка — отдельного действующего бюджета. Канонические источники toolkit изменяются при разработке, импортированный upstream-снимок в продукте сохраняется неизменным.

## 1. Проверенный источник

Выберите repository и точный commit, зафиксируйте дату и основание выбора. Получите отдельный временный clone с detached checkout нужного SHA; исходный рабочий checkout и его индекс не меняйте. Альтернатива — `git archive` точного commit в новый временный каталог. Архив не является checkout: поскольку validator использует Git-контекст, инициализируйте **только внутри отдельного временного архива** временный Git-репозиторий и индекс экспортированных исходников. Исходную ревизию подтвердите по Git blobs/manifest источника, а не по новому временному HEAD. Не добавляйте runtime в этот индекс.

Проверьте HEAD для clone, состав экспортированных файлов и отдельно их SHA-256/равенство исходнику. Для текущего рабочего target нужен явный manifest разрешённых исходников, включая новые файлы; один `git archive HEAD` не включает незакоммиченные изменения. Исключите `.git`, окружения, runtime, старые трассы и чужие untracked. Не очищайте дерево пользователя. Приёмка выбранного снимка предшествует импорту; старое доказательство не подтверждает изменённый снимок.

На отдельном снимке выполните с доступным Python 3.11+ и существующим PyYAML команды из [README](../README.md): unit tests, validator, `git diff --check`; прочитайте согласованность зависимостей и прав. Архивный временный индекс служит структурной проверке, не доказательством происхождения. Недоступную проверку сохраните с причиной и `result: null`. Разрешение на новые зависимости устанавливается отдельно, глобальная установка не требуется.

## 2. Preflight потребителя до записи

Установите фактический корень проекта, ветку/detached, HEAD, staged/unstaged/untracked, отпечаток индекса. Для `.agents`, `.agents/skills`, `.codex`, `.codex/agents` и каждого затрагиваемого потомка проверьте тип через lstat, цепочку родителей, реальную цель symlink/reparse point/junction, существующий Git-корень и worktree. Для отсутствующего пути проверяйте ближайшего существующего родителя. Сравните `git -C <каталог> rev-parse --show-toplevel` и `git worktree list --porcelain` с ожидаемым контекстом; имя `.codex` само по себе не доказывает отдельный репозиторий.

Составьте перечень существующих файлов, одноимённых скиллов, профилей, `expressa-*` расширений и конфигурации. Отделите несвязанные файлы и локальные изменения. Небезопасная цель, петля ссылки, внешний Git/worktree или конфликт существующего файла останавливают запись в затронутую область до разрешения. Не снимайте ссылки автоматически и не используйте рекурсивное удаление. Если снятие требуется, оформите отдельное разрешённое действие над самим объектом ссылки с сохранением цели. Подготовку можно продолжать в безопасном временном месте.

## 3. Комплект и зависимости

Полный комплект содержит 11 скиллов и 11 профилей (девять ответственностей и две Astra-вариации) из [каталога](../README.md). Выборочный импорт замыкается транзитивно по обязательным и применимым условным зависимостям:

| Процедура/профиль | Необходимый локальный источник |
|---|---|
| long-orchestration | orchestration-pact |
| product-quality | long-orchestration, orchestration-pact, UI-analysis-pact, web-verification |
| UI-analysis при документировании | documentation-pact |
| web-implementation | development-pact |
| debugging при исправлении | development-pact; диагностика без правок не включает исправление |
| любой профиль | канонический report в orchestration-pact; в dispatcher также long-orchestration |

Имена в таблице сокращены только для чтения; полный каталог использует префикс `codex-`. Прочитайте явные ссылки основных процедур и условные зависимости выбранного сценария. Не копируйте отдельный SKILL без его references, metadata, templates и нужных соседних каталогов. Отсутствие зависимости — точный блокер комплекта, глобальный одноимённый скилл не подставляется молча. Наличие полного комплекта означает доступность файлов, а не обязательную загрузку всего каталога в контекст.

После preflight скопируйте выбранные каталоги `skills/<имя>/` в `.agents/skills/<имя>/`, профили `agents/*.toml` — в `.codex/agents/`. Перед заменой существующего импорта сверяйте его прежний manifest и локальные изменения; не перезаписывайте их без разрешённого решения. Каждый файл импортированного скилла должен совпасть **по байтам** со снимком. Проектные расширения размещаются отдельно от upstream.

Канонические профили содержат ссылки `../skills/…`, рассчитанные от `agents/` toolkit. В проектных копиях замените только этот префикс на `../../.agents/skills/…`, рассчитанный от `.codex/agents/`; проверьте каждую Markdown-цель после разрешения ссылки, существование и принадлежность проекту. В частности, должны разрешаться report и long-orchestration. Сохраните исходные профили в снимке, а diff проектной адаптации перечислите отдельно. TOML разбирается независимо от проверки Markdown-ссылок. Модельные поля не добавляются автоматически.

## 4. Происхождение, правила и конфигурация

Создайте в проекте следующие долговременные файлы:

- `.agents/SOURCE.md`: repository, точный commit, дата импорта, вид снимка, импортированный комплект, список файлов, команды/коды фактических проверок и отдельные неизвестности. Для незакоммиченного target укажите исходный commit **и** идентификатор/manifest проверенного снимка; не приписывайте его байты одному HEAD.
- `.agents/upstream.sha256`: SHA-256 каждого импортированного исходного файла с путём относительно корня toolkit (`skills/…`, `agents/…`). Хеши upstream-профилей остаются хешами до адаптации. Проверьте полноту manifest и отдельно байты skill-копий; для адаптированных профилей сопоставьте исходник и разрешённый diff, сохраните хеш результата в LOCAL-ADAPTATIONS.
- `.agents/LOCAL-ADAPTATIONS.md`: перечень адаптированных профилей/путей/модельных настроек, причина, источник разрешения, SHA-256 результата и ссылки на проектные правила. Сами правила здесь не дублируются.

Короткий проектный `AGENTS.md` получает прямые локальные пути процедур из [фрагмента](../skills/codex-orchestration-pact/references/templates/AGENTS.fragment.md). Пути внутри его примера рассчитаны от корня потребителя. Обычная задача и `dispatcher_only` различаются. Подробные charter/preferences и доменные правила живут отдельно, с происхождением и статусом принятия. Существующие `expressa-*` расширения проверьте на противоречия и сведите к проектным уточнениям; второй автомат оркестрации не создавайте.

Standalone TOML и пути обнаружения описаны в [совместимости](compatibility.md). Существующие общие `[agents]`, `.codex/config.toml` и несвязанные параметры сохраняются. Не создавайте config только ради регистрации и не добавляйте `[agents.<role>]` из старого ТЗ. Изменение существующей регистрации требует отдельного обоснования и разрешённого diff. Проверяйте поддерживаемые поля по применимой версии клиента; настройки источника не доказывают эффективные права или модель.

## 5. Отслеживаемое и runtime

Исходные skill-копии, профили, SOURCE/manifest/LOCAL-ADAPTATIONS и долговременные правила должны отслеживаться проектом. Добавление в индекс/commit выполняется только при соответствующем разрешении; до него честный статус — «подготовлено, ещё не tracked». Политику существующего `.codex/config.toml` сохраняйте. Игнорируйте `.codex/tmp/` и выбранные runtime-каталоги, не весь `.codex`/`.agents` и не произвольный `state.yaml`: шаблоны внутри `references/templates` — исходники.

Проверьте конкретные пути командами ниже (полный импорт). Первая команда должна показать правило runtime; вторая — не показать совпадений и вернуть 1; третья показывает фактический индекс, четвёртая — ещё не отслеживаемые файлы. Успех `check-ignore` не доказывает tracked, а tracked-файл может скрывать ошибочное ignore-правило, поэтому используется `--no-index`.

```sh
git check-ignore -v --no-index .codex/tmp/tasks/discovery-check/state.yaml
git check-ignore -v --no-index .agents/SOURCE.md .agents/upstream.sha256 .agents/LOCAL-ADAPTATIONS.md .agents/skills/codex-long-orchestration/references/templates/state.md .agents/skills/codex-product-quality/references/templates/quality-state.yaml .codex/agents/quality-owner.toml
git ls-files -- .agents .codex/agents AGENTS.md
git ls-files --others --exclude-standard -- .agents .codex/agents AGENTS.md
git diff --check
```

Не переносите в приложение `tools/`, `tests/`, `evals/`, `requirements-dev.txt`, отчёты и документацию разработки toolkit как runtime-зависимости. Проверки источника выполняются на отдельном снимке. Итоговый diff/manifest должен отличать новые, изменённые и удалённые исходники от отдельного списка игнорируемых артефактов.

## 6. Проектные примеры Expressa

Следующие критерии — **подтверждённые примеры для Expressa из приложенного ТЗ**, а не общие нормы toolkit: низкая перегрузка; ясное действие восстановления в одном контексте ошибки; обоснование дублирующих/плавающих элементов; пользовательский текст вместо технического кода в основном сообщении; системная геометрия; проверка актуальности макета. Приоритет из ТЗ Expressa: **корректность → понятность → согласованность → доступность → визуальная точность**. Он не разрешает игнорировать обязательную доступность или безопасность.

Происхождение — объединённое ТЗ v3 §7.6 и реестр §15, см. [источники](sources.md). Его описание предоставленных снимков отмечает дублирование корзины/боковой навигации, разные ошибки/повторы и `INTERNAL_SERVER_ERROR` в основном сообщении. Это кандидаты будущей проверки класса проблем; текущие требования и причина в CSS/компонентах не установлены. В этом документе снимки и отдельные экспорты лично повторно не исследованы; имена, номера, заказы и бренд не переносятся в универсальные фикстуры.

История: ТЗ Expressa v2 закрепляло **девять** скиллов на `2aa634fd293ba236d4f03ca3d874d152cc0ea0e4`. Это не установщик нового состава 11/9. Новое подключение требует выбора и проверки нового снимка; прежний SHA не подменяется.

### 6.1. Текущая политика и историческая граница Expressa

Текущая поставляемая политика профилей и parent root находится в [справочнике оркестрации](../skills/codex-orchestration-pact/references/complex-task-orchestration.md#текущая-политика-поставляемых-профилей). Это единственный канонический источник для текущего toolkit; она не устанавливает настройки Expressa или наблюдаемые эффективные параметры клиента.

Историческая запись подтверждает только то, что ТЗ Expressa v2 закрепляло девять скиллов на `2aa634fd293ba236d4f03ca3d874d152cc0ea0e4`. Точная таблица моделей этого ТЗ среди доступных первичных материалов не сохранена; её нельзя реконструировать строками, добавленными в позднейшую поставку. Поэтому исторические сведения не являются второй модельной политикой и не меняют текущую [каноническую политику](../skills/codex-orchestration-pact/references/complex-task-orchestration.md#текущая-политика-поставляемых-профилей).

Первая версия и ответ ассистента в экспорте использовали другую таблицу Luna/Terra/Sol. По консолидации нет отдельного подтверждения пользователем всех позднейших замен. Adoption и доступность конкретных ID в проекте **не подтверждены**.

## 7. Отдельная доверенная сессия

После структурной и смысловой приёмки подготовьте отдельный минимальный синтетический Git-проект с проверенным импортом и нейтральным UI, используя [протокол evals](../evals/README.md). Исполняемый bootstrap, назначения, task-root и разрешённый бюджет готовятся до запуска по этому протоколу; их наличие проверяется механически. Это не поручение strict root сочинить назначения. Ожидания проверяющего остаются вне входов испытуемого.

Короткий текст **будущего запроса**, где пути/лимит заполняются по фактической подготовке:

```text
В новой доверенной сессии выполни один синтетический project-local smoke-check в подготовленном проекте. Root dispatcher_only; используй существующее bootstrap-назначение и task-root из манифеста запуска, ограничения и расход — из state.md. Подтверди фактические локальные источники, запуск quality_owner и обмен: роль сама пишет полный отчёт, root получает только envelope, независимый reviewer читает файл. Сохрани наблюдаемые события и хеши; неизвестное — unable_to_verify. Продукт не изменяй.
```

Перед отправкой зафиксируйте конкретный путь проекта/манифеста, версию клиента, доверие проекту, разрешение и предел стоимости одной попытки **с учётом делегирования**. Текущая доработка этот запрос не запускала и не даёт нового eval-бюджета. Исторический бюджет из evals не возобновляется автоматически.

Новая сессия отдельно подтверждает discovery локальных путей, фактическую загрузку профиля `quality_owner`, применённые параметры/права и наблюдаемый файловый обмен. Наличие файлов, список доступных имён и отсутствие маркера в финале не доказывают чтение/нечтение: нужны события инструментов/модели. При отсутствии наблюдаемости критерий — `unable_to_verify`. Глобальные одноимённые источники не считаются локальными; переносимость не означает доказанное отключение всех источников клиента. Только после подтверждения — отдельное разрешённое подключение и кампания в продукте. Поведение и сравнительная эффективность имеют независимые статусы.
